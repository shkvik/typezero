# Сравнение с Go

Одни и те же программы на typezero (`main.ts`) и на Go (`main.go`) в каждом каталоге.
Код на Go — прямой перевод, без оптимизаций, которых нет в версии на TypeScript.
Исключения — `concat_builder`: так задачу из `concat` решают на Go на практике, и `decimal`:
десятичного типа в Go нет, и точный счёт там ведут в `math/big.Int` (а `decimal_cents` — вручную
в `int64`).

| Каталог | Что измеряет |
|---|---|
| `empty` | запуск и вывод одной строки |
| `fib` | рекурсивные вызовы: `fib(35)` на 32-битных целых |
| `push` | 10 млн `push` в `int[]` (в Go — `append` в `[]int32`) |
| `sum` | `push` как в `push`, потом 20 проходов с суммированием |
| `generics` | то же, что `sum`, через обобщённые функции: `fold` с колбэком и поиск `indexOf` |
| `generic_classes` | обобщённые классы: 10 млн `push`/`pop` у `Stack<int>` и сортировка кучей миллиона чисел в `MinHeap<int>` (`MinHeap<T extends number>`; в Go — `Stack[T any]` и `MinHeap[T cmp.Ordered]`) |
| `queue` | 200 тыс. `push`, потом `shift` до пустого массива (в Go — `q = q[1:]`) |
| `sieve` | решето Эратосфена до 20 млн, `new Array<boolean>` |
| `words` | 1 млн коротких строк `` `w${i % 1000}` `` в массиве |
| `words_scan` | то же и `for...of` с `endsWith` по всем словам |
| `words_join` | то же и `join(",")` |
| `concat` | `s += "ab"` 200 тыс. раз; потом ещё 100 тыс. с `endsWith` после каждого |
| `concat_builder` | только Go: `concat` через `strings.Builder` |
| `binary-trees` | binary-trees из Benchmarks Game, глубина 18: около 68 млн маленьких объектов-узлов создаются, обходятся и освобождаются |
| `n-body` | n-body из Benchmarks Game: 5 млн шагов модели пяти планет, объекты с полями `double` |
| `cycles_list` | двусвязные списки: 20 списков по 500 тыс. узлов с `prev` и `next` строятся, обходятся в обе стороны, каждый десятый узел вырезается, и список бросают; в tz каждый список — одна группа (см. «Циклы ссылок» в README), в Go — сборщик |
| `cycles_tree` | деревья с `parent` и массивами `children`: 10 деревьев по 349 525 узлов (по 4 ребёнка, глубина 9), от каждого листа вверх до корня; в tz дерево вместе с массивами — одна группа |
| `decimal` | миллион цен `decimal` с копейками, потом 10 проходов `total += price * qty` и среднее. В Go — `math/big.Int` в копейках: точный счёт стандартной библиотекой, в цикле без выделений памяти (`t.Mul`, `total.Add` на месте) |
| `decimal_cents` | только Go: то же на `int64` в копейках, как считают вручную; на суммах больше 92 233 720 368 547 758.07 молча переполняется |
| `particles` | 300 частиц, 120 шагов, все пары: классы `Vec` и `Particle`, методы которых возвращают новые векторы — около 30 млн маленьких объектов через вызовы методов (в Go — методы с `*Vec`) |
| `iterators` | по 10 млн значений: `for...of` по генератору, `filter`/`map`/`take`/`reduce` над бесконечным генератором и над `values()` массива (в Go — итераторы `iter.Seq` и такие же функции над ними) |
| `regex_input` | только текст для `regex_*`: 20 МБ слов, чисел и дат из одной и той же последовательности (файлы tz пока не читает, поэтому каждая программа строит текст сама) |
| `regex_count` | `match(/[a-z]+ing/g)` — число совпадений (в Go — `FindAllStringIndex`) |
| `regex_dates` | `replace(/(\d{4})-(\d{2})-(\d{2})/g, "$3.$2.$1")` (в Go — `ReplaceAllString`) |
| `regex_dna` | `match(/agggtaaa\|tttaccct/gi)` — число совпадений без учёта регистра |
| `regex_words` | `match(/\b(?:error\|warning\|fatal)\b/g)` — число целых слов |
| `regex_groups` | `matchAll(/(\w+)ing (\w+)/g)` с группами: сумма длин второй группы (в Go — `FindAllStringSubmatch`) |
| `wordcount` | 20 МБ текста — 3,5 млн слов из слогов, 160 тыс. разных: `split(" ")`, подсчёт в `Map<string, int>` (в Go — `map[string]int`) и пять самых частых |
| `shapes` | миллион фигур четырёх классов-наследников абстрактного `Shape` вперемешку в одном массиве и 20 проходов с `area()` и `perimeter()` через `Shape` — вызовы через таблицу методов (в Go — через интерфейс) |
| `unions` | то же на объединении `Circle \| Rect \| Square \| Triangle` обычных объектов с меткой `kind` и `switch` по ней, и миллион значений `int \| string` с `typeof` (в Go — `switch` по типу структур за интерфейсом и по `any`) |
| `async_await` | миллион `await` async-функции, которая заканчивает сразу, и миллион `await` простого значения (в Go — запрос и ответ горутине по каналам без буфера и `runtime.Gosched()`, на одном ядре, как node) |
| `async_tasks` | 100 тыс. задач сразу, каждая 10 раз ждёт `await`, потом `Promise.all` их результатов (в Go — 100 тыс. горутин с `runtime.Gosched()` и `sync.WaitGroup`) |
| `async_parallel` | 64 задачи сразу, каждая после `await` считает простые числа в своём отрезке, потом `Promise.all` — расчёт на всех ядрах (параллельный рантайм, docs/async.md, раздел 8; в Go — горутина на задачу и `sync.WaitGroup`) |
| `async_timers` | 200 тыс. таймеров на 1–10 мс, каждый четвёртый сразу отменён, и ожидание остальных (в Go — `time.AfterFunc` и `Stop`) |
| `bytes_checksum` | 100 МБ в `Uint8Array`: заполнение, `^=` с ключом из 16 байт, сумма и 32-битный FNV-1a — по циклу на каждое (в Go — `[]byte`) |
| `base64` | 30 МБ случайных байт: `Buffer` в base64 и обратно пять раз и один раз в hex и обратно (в Go — `encoding/base64` и `encoding/hex`) |
| `bytes_records` | 4 млн записей по 16 байт через `DataView`: `uint32` и `float64` в little-endian, два `uint16` в big-endian; запись, пять проходов чтения и проход через `readUInt32LE` / `readDoubleLE` у `Buffer` над тем же `ArrayBuffer` (в Go — `encoding/binary`) |

| `str_join` | `join` 4,4 млн слов и 256 тыс. строк того же лога, по десять раз |
| `str_search` | `includes`, `indexOf`, `lastIndexOf`, `startsWith`, `endsWith` в каждой строке лога, пять раз, и 20 поисков отсутствующих слов во всём тексте |
| `str_slice` | `slice` и `substring` каждой строки лога (дата, время, уровень, сообщение, конец строки), пять раз; в Go — `s[a:b]` |
| `str_case` | `toUpperCase` и `toLowerCase` строк лога (три раза), его слов и 800 тыс. слов с буквами Latin-1 (`é`, `ö`) |
| `str_trim` | `trim`, `trimStart` и `trimEnd` строк лога с пробелами и табуляцией по краям, пять раз, и всех его слов |
| `str_replace` | `replaceAll` со строками: разделители и слова всего лога, пять раз, и пробелы каждой строки |
| `str_chars` | символы лога по одному: `charCodeAt(i)` три раза, `s[i]` и `for...of` по два (в Go — `text[i]` и `range`) |
| `str_sort` | `sort()` 544 тыс. слов из восьмой части лога и `<` между соседями (в Go — `sort.Strings`) |
| `str_numbers` | миллион целых и три миллиона `double` в строки (шаблоны, `String`, `toFixed(2)`), потом `parseInt`, `Number` и `parseFloat` по миллиону строк (в Go — `strconv`) |

| `crypto_sha256` | 2 ГиБ через SHA-256 кусками по 1 МиБ (в Go — `crypto/sha256`) |
| `crypto_aes_gcm` | 2 ГиБ шифрования AES-256-GCM: 131 072 сообщения по 16 КиБ (запись TLS), у каждого свой nonce, — новый `createCipheriv` на каждое (в Go — `cipher.NewGCM` и `Seal` в один буфер) |
| `crypto_rsa_sign` | 3000 подписей RSA-2048 с SHA-256 и PKCS#1 v1.5 (в Go — `rsa.SignPKCS1v15`) |
| `crypto_ecdsa_sign` | 50 000 подписей ECDSA P-256 с SHA-256 (в Go — `ecdsa.SignASN1`) |
| `crypto_ed25519_sign` | 50 000 подписей Ed25519 (в Go — `crypto/ed25519`) |
| `crypto_x25519` | 50 000 обменов ключами X25519 между одними ключами (в Go — `crypto/ecdh`) |
| `di_known` | маленький DI: 5 млн раз `make(Handler)` (`Reflect.construct(cls, [])` в `make<T>(cls: Constructor<T>)`) и два вызова метода через `Reflect.get(obj, "handle")` и `Reflect.apply` — класс известен при компиляции (в Go — `&Handler{}` и прямой вызов) |
| `di_reflect` | то же с классом из `Constructor[]`, известным только при выполнении: через описание класса в exe (в Go — `reflect.New`, `MethodByName` и `Call`) |
| `subtle_sha256` | 2 ГиБ через `crypto.subtle.digest("SHA-256")`: 128 кусков по 16 МиБ разом через `Promise.all` (в Go — горутина на кусок с `sha256.Sum256` и `sync.WaitGroup`) |
| `subtle_hmac` | 200 000 подписей HMAC-SHA256 сообщений по 1 КиБ одним ключом, по 1000 разом через `Promise.all`, как сервер проверяет запросы (в Go — горутина на подпись с `hmac.New`) |

## Как запустить

Нужны собранный `tz` (`build/dev/bin/tz.exe`) и Go. Из корня репозитория:

```
powershell -NoProfile -File bench\run.ps1
powershell -NoProfile -File bench\run.ps1 -Names fib,sieve -Runs 15
powershell -NoProfile -File bench\run.ps1 -Go D:\Programs\Go\bin\go.exe
```

Скрипт собирает всё в `bench/out` (`tz build` и `go build`), проверяет, что обе версии
печатают одно и то же, и выводит лучшее время из `-Runs` запусков (по умолчанию 7) и пиковый
рабочий набор процесса. Время — полное, от запуска процесса до выхода. Go собирается с
`GOAMD64=v1`, если переменная не задана: tz тоже генерирует код для базового x86-64.

`subtle_*` (Web Crypto) измерены 24 октября 2026. Работа идёт в пуле потоков рантайма, как в
node: 4 потока (`UV_THREADPOOL_SIZE`), а Go раскладывает горутины на все 32 ядра машины — отсюда

буфер, пока идёт работа), поэтому у `subtle_sha256` в памяти вдвое больше: куски и их копии;
сам SHA-256 — те же 2,7 ГБ/с на поток. node 24 на тех же программах — 891 и 1162 мс. Размер exe —
397 и 477 КБ (прямой слой OpenSSL) против 2.3 МБ у Go.

Откуда разница:

- **Короткие строки.** Строка до 8 однобайтовых символов хранится прямо в значении, без
  выделения памяти и без счётчика ссылок; `` `w${i}` `` собирается в регистре. В Go каждая такая
  строка — отдельный объект в куче. Поэтому `words*` вдвое быстрее и занимают вдвое меньше.
- **`concat`.** В Go строки неизменяемы, и `s += "ab"` копирует всю строку: цикл квадратичен.
  В tz `+=` дописывает в запас буфера, как `strings.Builder`, но без отдельного API.
- **Память массивов.** Данных одинаково: 10 млн 32-битных чисел. Пик у Go выше из-за сборщика
  мусора: старый буфер после роста живёт до сборки, а куча может вырасти вдвое против живых
  данных (`GOGC=100`). В tz старый буфер освобождается сразу при росте.
- **`sum`, `sieve`.** Компилятор доказывает, что индексы в пределах массива, и не вставляет
  проверок; LLVM векторизует цикл суммирования. Go проверки границ здесь тоже убирает, но
  векторизации у него нет.
- **`generics`.** Обобщённая функция компилируется копией под свои типы: `fold<int, long>` —
  тот же код, что написанный руками для `int[]` (оптимизированный IR совпадает), поэтому LLVM
  так же встраивает в него колбэк и векторизует цикл, и время — как у `sum`.
- **`generic_classes`.** Экземпляр обобщённого класса — класс, написанный для своих типов:
  `Stack<int>` держит `int[]`, а `h[r] < h[l]` у `MinHeap<int>` — сравнение целых. Методы
  `Stack<int>` дают тот же оптимизированный IR, что у класса `IntStack`, написанного руками, и
  встраиваются в цикл. У Go для `int32` тоже своя копия кода, и время одинаковое: около 28 мс —
  стек, остальное — куча. Память — как у `push`: старый буфер освобождается сразу при росте.
- **`fib`.** Только вызовы функций. У Go каждый вызов в том числе проверяет, хватает ли стека
  горутины.
- **`binary-trees`.** Узел освобождается, как только умирает последняя ссылка на него, и его блок
  сразу идёт под следующий узел; сборщику Go приходится снова и снова обходить долгоживущее
  дерево и держать кучу с запасом. Узел у tz — 32 байта (счётчик, описание, две ссылки), у Go —
  16 байт плюс служебные данные сборщика.
- **`iterators`.** Генератор, который перебирают там, где вызвали, встраивается в цикл, а цепочка
  методов итератора становится одним циклом с встроенными колбэками: в IR нет ни объектов, ни
  вызовов, и LLVM векторизует циклы по `range` и по `values()`. В Go каждое значение проходит
  через замыкания `yield` каждого шага цепочки. node на той же программе — около 550 мс: у него
  каждый шаг — объект, а значение — вызов `next()` и объект `{ value, done }`.
- **`n-body`.** Поля `double` лежат без упаковки по постоянным смещениям, и цикл получается из тех
  же инструкций, что у Go: разница в пределах разброса.
- **`decimal`.** Цена с копейками помещается в короткую форму `decimal` — 64-битное целое и
  масштаб прямо в значении, 16 байт в массиве. `price * qty` и `total +=` встроены в цикл как
  умножение и сложение целых с проверкой переполнения, без вызовов и выделений памяти, поэтому
  точный счёт стоит столько же, сколько `int64` в копейках вручную (`decimal_cents`). `big.Int` в
  Go — указатель на объект со слайсом цифр: каждая операция идёт через общий код многословной
  арифметики, а миллион цен — миллион объектов в куче.
- **`shapes`.** Вызов переопределённого метода — те же две загрузки (описание объекта и код из
  его таблицы методов) и косвенный вызов, что и вызов через интерфейс Go (там — из `itab`
  интерфейсного значения). Около 20 мс из 136 — создание миллиона объектов. В цикле tz ещё
  увеличивает и уменьшает счётчик ссылок каждой фигуры: компилятор не доказывает, что вызов метода
  не меняет массив. Память меньше: элемент массива — 8-байтная ссылка, у Go — 16-байтное
  интерфейсное значение, плюс запас кучи сборщика.
- **`cycles_*`.** Узлы — члены групп: перед узлом 16 байт (вожак и следующий член кольца).
  `tail.next = node` сливает группу нового узла с группой списка (меньшая присоединяется к
  большей, здесь за один шаг), а `node.prev = tail` внутри группы ничего не считает. Список или
  дерево освобождается целиком, когда снаружи на него не остаётся ссылок: два прохода по кольцу,
  второй — по 16 цепочкам сразу. Go чуть быстрее: его сборщик работает параллельно на других
  ядрах, а tz делает всё в одном потоке; памяти у tz на четверть–треть меньше — она
  освобождается сразу. Без групп (раньше такие циклы не освобождались) было около 140 и 120 мс,
  но 350 и 324 МБ.
- **`particles`.** Методы классов вызываются напрямую и встраиваются, объект получает `this`
  взаймы, без счётчика ссылок. Временный вектор освобождается сразу, и его блок идёт под
  следующий: память не растёт. Go тоже встраивает методы, но большая часть `&Vec{...}` уходит в
  кучу, и её разбирает сборщик.

- **`regex_*`.** Каждая регулярка-литерал в tz — своя функция поиска в машинном коде
  ([codegen_regex_native.cpp](../src/codegen/codegen_regex_native.cpp)). За вычетом построения
  текста (`regex_input`) на сами регулярки уходит у tz 36, 17, 5, 16 и 60 мс (`count`, `dates`,
  `dna`, `words`, `groups`; интерпретатору нужно было 119, 47, 66, 51 и 189), у Go — 431, 349,
  508, 353 и 593 мс; node на таком же тексте тратит 48, 20, 5, 9 и 70 мс (в одном процессе, см.
  README). Начало совпадения ищется по 32 байта за раз по байтам на одном–трёх смещениях от
  начала (у дат — `-` на смещении 4), выбор `error|warning|fatal` смотрит на символ и не ставит
  точек возврата, буквы подряд сравниваются по 8 байт (`agggtaaa` с `i` — одно сравнение), а с
  `g` один вызов находит сразу много совпадений. Go ищет автоматом без машинного кода и медленнее
  на каждом тесте. На `words` tz медленнее node: там больше всего стоят сотни тысяч
  строк-совпадений в массиве, а не поиск. `regex_groups` создаёт объект на каждое совпадение, как
  node; `matchAll` — ленивый итератор, и `for...of` по нему — цикл, где каждое совпадение
  освобождается до следующего: в памяти только текст.
- **`crypto_*`.** Алгоритм с именем в коде — прямой вызов функций OpenSSL (хеш, шифр), без поиска
  по имени в его таблицах; ключи и подписи идут через общий API OpenSSL, как в node. Go быстрее
  только на Ed25519: у него своя оптимизированная реализация, у OpenSSL этот код на C.
- **`unions`.** Метка (`kind: "circle"`) лежит у всех членов объединения на одном месте, сразу за
  заголовком объекта, а её значение — номер литерала: `switch (s.kind)` — одна загрузка и
  `switch` LLVM по числам, без сравнения строк. `int | string` хранится без упаковки, 24 байта
  в массиве (метка и строка в двух словах), и `typeof` — сравнение метки. В Go каждое `int32` в
  `any` — отдельный объект в куче, а `switch` по типу сравнивает указатели на описания типов.
- **`async_*`.** Вызов async-функции — один объект (`Promise` и фрейм корутины вместе), `await`
  значения не выделяет ничего, а продолжение — вызов функции корутины из очереди микрозадач. У Go
  каждое ожидание — переключение горутин планировщиком, а у каждой горутины свой стек (от 2 КБ,
  при росте копируется): 100 тыс. задач — 394 МБ против 23 МБ у tz, где задача вместе с массивами
  вокруг — меньше 200 байт. Таймер tz — объект в 88 байт в списке своей длительности, как в node;
  у Go — таймер рантайма и горутина на каждый сработавший `AfterFunc`. node на тех же программах —
  около 100, 180 и 115 мс (из них около 50 мс — запуск).
- **`bytes_checksum`.** Длину и указатель на байты компилятор читает с другой меткой TBAA, чем
  сами байты, поэтому запись байта их не портит: LLVM выносит их из цикла и делает заполнение,
  `^=` с ключом (`key[i & 15]` без проверки: маска меньше доказанной длины) и сумму векторными
  (`<16 x i8>`). Go проверки здесь убирает, но не векторизует. Больше половины времени у tz
  (около 140 мс) — два прохода FNV-1a: цепочка умножений, где каждое ждёт предыдущее, и её не
  векторизует никто.
- **`base64`.** Кодирование и разбор — по таблицам, как в node (`nbytes`): группа из 3 байт — 4
  символа, разбор сначала идёт быстрым путём без пробелов и `=`. Строка base64 однобайтовая и
  собирается прямо в своём буфере, `Buffer.from` — одно выделение памяти; текст и `back` прошлого
  раунда освобождаются сразу, поэтому пик памяти почти вдвое меньше, чем у Go со сборщиком.
- **`bytes_records`.** Цикл `off + 16 <= view.byteLength` доказывает, что все смещения
  `getUint32(off)` … `getUint16(off + 14)` и `readDoubleLE(off + 4)` в пределах, и каждое чтение
  или запись — одна невыровненная загрузка (у big-endian ещё `bswap`) без проверок. Go оставляет
  на каждом `binary.LittleEndian.Uint32(data[off:])` по две проверки границ (среза и длины).
  `Buffer.from(view.buffer)` делит память, как в node (в Go — `data[:]`).
- **`str_split`, `str_join`, `str_replace`.** `split` сначала считает разделители (по 16 байт за
  раз, SSE2), создаёт массив сразу нужной длины и пишет куски прямо в него: слово до 8 символов
  собирается в значении одной загрузкой 8 байт, кусок от 13 символов ссылается на исходный текст, и
  только куски из 9–12 символов — отдельные блоки памяти. `join` и `replaceAll` считают длину
  результата заранее и пишут его в один буфер по байту на символ, короткую строку — целым словом.
  Подстрока в Go — ссылка в текст, но сборщик держит кучу с запасом: памяти у Go вдвое больше.
- **`str_search`.** Поиск символа и подстроки идёт по 16 байт за раз; кандидаты для подстроки —
  места, где совпали и первый, и последний её символ, так что в тексте из похожих слов почти нет
  лишних проверок. `includes` или `indexOf` на строке лога — около 4 нс.
- **`str_slice`.** Медленнее Go: подстрока в Go — указатель и длина, а в tz кусок до 8 символов
  собирается в значении, кусок от 13 символов ссылается на строку (счётчик ссылок растёт), а кусок
  из 9–12 символов копируется в новый блок — здесь это дата `2026-10-24` в каждой строке. Сами
  вызовы `slice` и `substring` — 2–3 нс.
- **`str_case`.** У короткой строки регистр меняется у всех восьми байт сразу несколькими операциями
  над словом; у длинной ASCII-строки — циклом, который LLVM векторизует; буквы Latin-1 (`é` → `É`) —
  тем же побайтовым путём, без перекодирования. `strings.ToUpper` в Go разбирает UTF-8 и выделяет
  память под каждый новый результат.
- **`str_chars`.** Медленнее Go: `text` здесь — константа верхнего уровня, то есть глобальная
  переменная, и цикл перечитывает её на каждом шаге, а проверки вида строки (буфер, короткая, rope)
  остаются в цикле. С локальной строкой `charCodeAt` по тем же 21 МБ — 4 мс против 3,6 мс у Go.
- **`str_sort`.** Сравнение однобайтовых строк почти всегда решается по первым восьми символам
  одним сравнением слов; медленнее Go здесь сама сортировка слиянием в рантайме (в Go — pdqsort).
- **`str_numbers`.** Число в строку — алгоритм Ryū: кратчайшие цифры, которые читаются обратно в то
  же число, а из них ближайшие, как у V8 (раньше tz перебирал точность через `snprintf` и `strtod` и
  был в 12 раз медленнее Go). Строка в число — без `strtod` и без копирования текста, когда цифры
  помещаются в 2⁵³, а степень десяти — не больше 22 (точный путь Клингера).
- **`di_known`, `di_reflect`.** В копии `make` для `Handler` `Reflect.construct(cls, [])` — это
  `new Handler()`, а в копии `invoke` `Reflect.get(obj, "handle")` даёт функцию метода в коробке,
  которая живёт всю программу, и `Reflect.apply` её — прямой вызов `obj.handle(n)` без проверок:
  остаются объект и коробка для результата `unknown` (Go кладёт `Handler` на стек). Через описание
  — поиск метода по имени, проверка `this`, аргументы и результат в `unknown` с проверкой каждого;
  `reflect` у Go на том же в 5,6 раза медленнее и держит 120 МБ мусора.
- **`fsp_files`.** Почти всё время — системные вызовы: открыть, прочитать и закрыть файл в Windows
  стоит около 90 мкс (`readFileSync` подряд — 900 мс). tz делает их в пуле из 4 потоков, как node
  (`UV_THREADPOOL_SIZE`), каждый `readFile` — одна работа для пула; Go — на всех ядрах, сколько
  горутин стоят в вызове, столько и потоков. С `UV_THREADPOOL_SIZE=16` tz — 58 мс против 84 мс у Go,
  с 1 потоком — 256 мс против 312 мс у Go с `GOMAXPROCS=1`. Буфер под файл — ровно его размер:
  блоки по 64 КБ куча Windows выдаёт потокам по очереди, и с ними 4 потока работали почти вдвое
  медленнее. node на этой программе падает с `EMFILE`: его `readFile` — четыре похода в пул, и
  сначала он открывает все 10 тыс. файлов, а в Windows больше 8192 открытых нельзя.

Цифры с одной машины и одного запуска скрипта. Разброс между запусками заметный, у обоих
языков до 20% на тестах в десятки миллисекунд, поэтому сравнивать стоит прогоны одного запуска.

## HTTP

`http_hello` — сервер «Hello, World!» на tz (`serve` из `tz:http`), Go (`net/http`) и node
(`node:http`), и `http_load` — нагрузка на Go, как у bombardier: 128 соединений с keep-alive шлют
запрос за запросом 10 с ([net.md](../docs/net.md), раздел 6). `run.ps1` пропускает каталоги
`http_*`: сервер работает, пока его не остановят. Запуск:

```
powershell -NoProfile -File bench\http.ps1 -Go D:\Programs\Go\bin\go.exe [-Connections 128] [-Seconds 10]
```

AMD Ryzen 9 9950X3D, Windows 11, Go 1.23.4, node 24, 25 октября 2026; нагрузка — на той же машине.

| Сервер | запросов в секунду | задержка | ядра |
|---|---:|---:|---|
| tz | 314 000 | 0,41 мс | все (параллельный рантайм) |
| Go (`net/http`) | 239 000 | 0,54 мс | все |
| node (`node:http`) | 61 000 | 2,1 мс | одно |

Запрос целиком — разбор, обработчик, ответ — выполняет поток пула, который его прочитал
([async.md](../docs/async.md), раздел 8). 24 октября, когда всё шло в главном потоке, у tz было
76 000. Обработчик, который трогает общие данные, идёт в порядке node через главный поток: со
счётчиком в глобальной переменной — около 92 000.
