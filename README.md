# typezero

Язык с синтаксисом TypeScript, который компилируется в нативный исполняемый файл, как Go.
Компилятор `tz` написан на C++ и генерирует код через LLVM; линковщик LLD встроен в него.

```ts
function fib(n: int): int {
  if (n < 2) return n
  return fib(n - 1) + fib(n - 2)
}

console.log("fib(30) =", fib(30))
```

```
tz run fib.ts            # скомпилировать и запустить
tz build fib.ts          # получить fib.exe
tz build -O0 fib.ts      # без оптимизаций (по умолчанию -O2)
tz build --emit-llvm fib.ts   # посмотреть LLVM IR (fib.ll)
```

Примеры программ лежат в [examples](examples): типы и преобразования, строки, массивы,
Фибоначчи, простые числа, последовательность Коллатца. Сравнение скорости и памяти с Go на
одинаковых программах — в [bench](bench).

## Что уже работает

- Типы `int` (32 бита), `long` (64 бита), `double` (он же `number`), `boolean`, `string`, `void`.
- Функции с аннотированными параметрами, рекурсия, вызов до объявления.
- `let` / `const`, блочная область видимости, глобальные переменные верхнего уровня.
- `if` / `else`, `while`, `do ... while`, `for`, `for...of` (по массивам и по кодовым точкам
  строк), `break`, `continue`, `return`.
- Арифметика, сравнения, `&&` / `||` с коротким замыканием, побитовые операции и сдвиги,
  `?:`, `++` / `--`, составное присваивание, преобразования `as`.
- Строки с семантикой JS: `+` и `+=` (числа и `boolean` превращаются в строку), шаблонные
  строки `` `x = ${x}` ``, сравнения, `.length`, `s[i]`, `charCodeAt`, `slice`, `substring`,
  `indexOf`, `includes`, `startsWith`, `endsWith`, `repeat`, `String(x)`, `x.toString()`.
- `undefined` и тип `T | undefined`: сравнения `=== undefined`, `??`, `??=`, сужение типа
  после проверки (`if (x !== undefined) x + 1`). Функция с типом `T | undefined` может просто
  закончиться — она вернёт `undefined`.
- Массивы `T[]` (или `Array<T>`) любых из этих типов, вложенные: литералы `[1, 2]` и
  `[...a, x]`, `a[i]`, `a[i] = x`, `.length` (чтение и запись), `new Array<T>(n)`, `push`, `pop`,
  `shift`, `unshift`, `at`, `slice`, `concat`, `indexOf`, `lastIndexOf`, `includes`, `join`,
  `reverse`, `fill`, `sort()` (без функции сравнения), `toString`.
- `console.log` с любыми из этих типов; массивы печатаются ровно как в Node.js.
- Необязательные точки с запятой (ASI), комментарии, escape-последовательности.

Код верхнего уровня — это точка входа программы.

## Строки и память

Длина и индексы строк считаются в единицах UTF-16, как в JS: `"привет".length` — 6,
`"😀".length` — 2. Внутри строка — значение из двух слов (указатель и длина с флагами), а
данные хранятся как в V8: по байту на символ, если хватает Latin-1, иначе по два. Строка до 8
таких однобайтовых символов лежит прямо в значении, на месте указателя: `"w" + i` или `s[i]`
не выделяют памяти, и счётчика ссылок у такой строки нет. Подстроки
длиной от 13 символов не копируются, а ссылаются на исходную строку. Длинная конкатенация
создаёт rope (узел из двух частей), которая склеивается при первом чтении в буфер с запасом
места, а следующие `+=` дописывают в этот запас. Поэтому сборка строки через `+=` линейна, даже
если строку читают между дописываниями (V8 на таком цикле квадратичен).

Память строк и массивов освобождается подсчётом ссылок, без сборщика мусора. Литералы лежат
в exe и не считаются. Переменная освобождает своё значение при выходе из области видимости и
при присваивании, массив — свои элементы, когда умирает сам. В конце программы память
отдаёт операционная система, без обхода всех объектов. С переменной окружения
`TZ_CHECK_LEAKS=1` программа, наоборот, освобождает всё и сообщает о неосвобождённых объектах;
тесты запускаются именно так.

Память выделяет собственный аллокатор рантайма (как mimalloc, упрощённый для одного потока):
сегменты по 4 МБ, выровненные на 4 МБ, страницы по 64 КБ для блоков одного размера, большие
объекты — отдельными кусками у ОС. Выделение и освобождение маленького блока — несколько
инструкций; на миллионах строк это вдвое быстрее `malloc` из C.

## Массивы

Массив — ссылка, как в JS: после `let b = a; b.push(1)` новый элемент видно и через `a`.
Элементы хранятся без упаковки по статическому типу: `int[]` — подряд лежащие 32-битные числа,
`boolean[]` — по байту, `string[]` — по 16 байт. Видов элементов, переходов между ними и дыр,
как в V8, нет: тип известен при компиляции. Новый массив — одна аллокация (заголовок и
элементы рядом), при росте элементы переезжают в отдельный буфер с запасом в полтора раза.
`shift()` сдвигает начало и не копирует элементы, `unshift()` оставляет запас спереди, так что
очередь и дек работают за O(1) на операцию (в V8 `shift` на массивах больше ~16 тысяч
элементов копирует весь массив).

**Индексы.** Если компилятор доказал, что индекс в пределах массива или строки, `a[i]` имеет
тип элемента и читается без проверки. Иначе, как в JS, результат может быть `undefined`, и тип
— `T | undefined`:

```ts
for (let i = 0; i < a.length; i++) sum += a[i]   // int, проверки нет
if (i >= 0 && i < a.length) use(a[i])           // int
const x = a[n]                                   // int | undefined
total += a[n] ?? 0
```

Компилятор следит за фактами вида `i < a.length`, `i >= 0`, `a.length === n + 1`: их дают
условия, объявления и присваивания, проверки вида `if (i >= a.length) return`, циклы с шагом
`++`, `--` или постоянным `+= k`. Факт забывается, когда то, о чём он, может измениться:
присваивание, `pop()`, вызов функции (она может изменить глобальные переменные и любой массив).
Целые числа заворачиваются при переполнении, поэтому `i + 1` считается без переполнения, только
если это доказано; индексы и позиции вычисляются в 64 битах. В тех же правилах `pop()` и
`shift()` дают `T`, если массив заведомо не пуст, а `charCodeAt` за пределами строки — `double`,
потому что JS возвращает `NaN`.

**Запись** `a[i] = x` разрешена, если доказано `i <= a.length` (`a[a.length] = x` добавляет
элемент, как в JS); дальше в JS остались бы дыры, поэтому без доказательства — ошибка
компиляции с подсказкой проверить индекс или использовать `push()`.

## Чем отличается от TypeScript

- Есть целые типы. `7 / 2` для `int` равно `3`; переполнение целых заворачивается, как в Go.
- Деление целого на ноль — паника: сообщение в stderr и код выхода 2.
- Неявных преобразований с потерей нет: `int` сам расширяется до `long` и `double`, всё
  остальное — через `as`. `as` действительно преобразует значение: `double as int` отбрасывает
  дробную часть и насыщается на границах (NaN → 0).
- Целочисленный литерал принимает тип из контекста: `let x: double = 1 / 2` даёт `0.5`.
- Условия в `if` / `while` / `for` / `?:` обязаны быть `boolean`.
- Без аннотации тип возврата функции — `void`, а не выведенный.
- `var` нет.
- `.length`, результаты `indexOf` и `charCodeAt` — типа `int` (`charCodeAt` с недоказанной
  позицией — `double`, см. «Массивы»).
- Объединения типов — только `T | undefined`; `null` нет. `as` не убирает `undefined`: для
  этого есть проверка или `??`.
- `[]` без типа — ошибка: нужен тип элементов (`let a: int[] = []`). `int[]` нельзя присвоить в
  `double[]` — у них разное представление в памяти; tsc считает оба `number[]`.
- В массивах нет дыр: `new Array<int>(3)` — это `[0, 0, 0]`, а не три пустых места; увеличение
  `length` дописывает нули, `false`, `""` или `undefined`. Такой `new Array(n)` есть только для
  этих типов элементов.
- Методы с функциями (`map`, `filter`, `forEach`, `sort` с компаратором) появятся вместе со
  стрелочными функциями.
- `new Array(-1)` и отрицательная длина — паника `RangeError`, как необработанное исключение в
  JS.

## Сборка

Нужно (Windows x64):

- Visual Studio 2022 или Build Tools с компонентом C++ (MSVC, CMake, Ninja).
- LLVM 23.1.4 — архив `clang+llvm-23.1.4-x86_64-pc-windows-msvc.tar.zst` с
  [GitHub releases](https://github.com/llvm/llvm-project/releases/tag/llvmorg-23.1.4)
  (не `.msi`: в инсталляторе нет библиотек для разработки). Архив сжат с длинным окном,
  встроенный `tar` его не открывает: `zstd -d --long=31 -c архив | tar -xf - --strip-components=1`.
- [vcpkg](https://github.com/microsoft/vcpkg): из него приходят zlib, zstd и libxml2, которые
  нужны LLVM, но не входят в архив.

Пути задаются переменными окружения `LLVM_ROOT` и `VCPKG_ROOT` или в локальном
`CMakeUserPresets.json` (он в `.gitignore`):

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "dev",
      "inherits": "windows",
      "environment": { "VCPKG_ROOT": "D:/Programs/vcpkg", "LLVM_ROOT": "D:/Programs/LLVM" }
    }
  ],
  "buildPresets": [{ "name": "dev", "configurePreset": "dev" }],
  "testPresets": [{ "name": "dev", "inherits": "windows", "configurePreset": "dev" }]
}
```

В «x64 Native Tools Command Prompt for VS 2022»:

```
cmake --preset dev
cmake --build --preset dev
ctest --preset dev
```

Результат — `build/dev/bin/tz.exe` и рядом `tzrt.lib` (рантайм, который линкуется в каждую
программу). Готовый LLVM собран в Release со статическим CRT, без RTTI и исключений, поэтому
`tz` собирается так же; Debug-сборка не поддерживается.

## Как устроен компилятор

```
.ts → Lexer → Parser → AST → Sema → CodeGen → LLVM IR → оптимизации → .obj → LLD → .exe
```

| Каталог | Что внутри |
|---|---|
| `src/lex` | токены и лексер |
| `src/parse` | парсер рекурсивным спуском, ASI |
| `src/ast` | узлы AST и символы |
| `src/sema` | типы, разрешение имён, проверка типов; неявные преобразования становятся узлами `CastExpr`; факты и доказательства индексов (`Facts.cpp`, `SemaFlow.cpp`) |
| `src/codegen` | генерация LLVM IR через `IRBuilder`; массивы — `CodeGenArray.cpp` |
| `src/driver` | командная строка, пайплайн оптимизаций, объектный файл, встроенный LLD |
| `runtime` | рантайм на C: аллокатор (`alloc.c`); вывод, форматирование чисел, паника (`tzrt.c`); строки (`string.c`); массивы (`array.c`); `console.log` для массивов как в Node (`inspect.c`) |
| `tests` | `run/*.ts` с ожидаемым выводом в `*.out`; `errors/*.ts` с `// expect-error:` |
| `bench` | одни и те же программы на typezero и Go и скрипт сравнения |

## Тесты

Каждый `tests/run/name.ts` компилируется с `-O0` и `-O2`, запускается с проверкой утечек, и
stdout сравнивается с `name.out`. Код выхода и stderr задаются комментариями `// expect-exit: N` и
`// expect-stderr: текст`. Каждый `tests/errors/*.ts` обязан не скомпилироваться, а на строке под
комментарием `// expect-error: текст` должна быть ошибка с этим текстом (так проверяется, что
каждая ловушка в [tests/errors/bounds.ts](tests/errors/bounds.ts) поймана отдельно).

Тесты с первой строкой `// same-as-node` ведут себя ровно как JavaScript: если установлен Node.js
23.6 или новее (он сам отбрасывает типы), они дополнительно запускаются в `node` и должны
напечатать тот же `name.out`. Так ожидаемый вывод сверяется с эталонной реализацией.
