# Async

Решения, принятые 21 и 23 октября 2026 года, и поправки 26 октября: `Promise` не отклоняется,
асинхронная ошибка — `Promise<Result<T, E>>` ([errors.md](errors.md), раздел 4). Шаги 1–4 плана
сделаны 24–25 октября, шаг 7 — 27 октября; что осталось — в конце, в разделе «План реализации».

## Коротко

- `async` / `await` по умолчанию выполняются параллельно на всех ядрах, без пометок. Память
  общая. `go`, каналов и ручных потоков нет.
- Результат программы — такой, какой мог бы выдать node. Программа без ввода-вывода печатает
  одно и то же на каждом запуске, ровно как node.
- Куски кода, которые трогают одни и те же изменяемые данные, идут по очереди в порядке node,
  остальные — параллельно. Компилятор показывает, что и почему идёт по очереди.
- `Promise`, которого никто не ждёт, — ошибка компиляции; «запустить и не ждать» — `void f()`.
  Задача, которую не ждут, разбирает свои ошибки сама.
- `Promise` и таймеры — как в node, но `Promise` никогда не отклоняется: ошибка лежит в
  `Result` внутри.
- Общий `Map`, который задачи меняют параллельно, — `ConcurrentMap` из `tz:sync` (раздел 9):
  каждое действие целое, порядок node между задачами не держит. Общие объекты (`shared`) и
  `Mutex` отложены.
- Данные, которые идут за запросом через все `await` (номер запроса, пользователь), —
  `AsyncLocalStorage` из `node:async_hooks` (раздел 10): только `run` и `getStore`, с правилами,
  которые держат хранилище внутри `run`.
- Соединения с базой и другие объекты, которыми пользуется одна задача за раз, — `Pool` из
  `tz:sync` (раздел 11): `use(async (item) => ...)`, объект живёт только внутри `use`.

## 1. Как это устроено в node

```ts
async function load() {
  const text = await readFile("a.txt", "utf8")   // load «засыпает» здесь
  console.log(text.length)                       // продолжение — когда текущий код закончится
}
```

JS выполняется в одном потоке. Ждёт не JS: файл читает ОС, ответ сети ждёт ОС. Очередей две:
- **события** — «файл прочитан», «пришёл ответ», «сработал таймер»;
- **микрозадачи** — продолжения после `await` и колбэки `.then`.

Цикл node: выполнить основной код целиком; дальше, пока есть чего ждать, — все микрозадачи, одно
событие, снова все микрозадачи и т.д. Работающий код никогда не прерывают, поэтому **между двумя
`await` никто не вмешивается**. Код на JS на это рассчитывает, и tz это сохраняет.

## 2. Что идёт параллельно

**Кусок** — код между двумя `await` (или от начала функции до первого `await`). Куски разных
задач идут одновременно, если не трогают одни и те же изменяемые данные: одна задача данные
меняет, а другая меняет или читает. Данные, которые все только читают, делятся свободно. Вывод
на экран — тоже общие данные: его «меняет» каждый, кто печатает.

Параллельно может пойти только то, чего программа не ждёт сама: `Promise.all`, несколько запросов
к серверу, `void f()`. Обычный код (циклы, `map` без `async`) компилятор сам не распараллеливает.

```ts
async function convert(file: string) {
  const text = await readFile(file, "utf8")
  const result = heavy(text)                // секунда расчёта, только свои данные
  await writeFile(file + ".out", result)
}
await Promise.all(files.map(f => convert(f)))
```

В node чтение и запись идут одновременно, а `heavy` — по одному: 4 файла ≈ 4 с. В tz четыре
`heavy` идут на четырёх ядрах ≈ 1 с.

| Что в куске | Как идёт |
|---|---|
| только свои данные (пример выше) | параллельно |
| расчёт, потом `done++` или `results.push(r)` | расчёт параллельно, по очереди только `done++` |
| прочитал общее → долго считаешь → записал общее (`cache.get` … `heavy` … `cache.set`) | по очереди: в JS между `get` и `set` никто не вмешается, и код на это рассчитывает |
| `console.log` → долго считаешь → `console.log` | по очереди: node никогда не напечатает «начал a», «начал b» подряд |
| расчёт сам пишет в общую таблицу | по очереди |
| `for (const f of files) await convert(f)` | по очереди по смыслу: программа сама ждёт каждый |

- **По очереди идёт только участок** от первого до последнего обращения к общим данным внутри
  куска, а не весь кусок и не вся функция.
- **Как ускорить «прочитал → считаешь → записал»** — так же, как в JS: поставить `await` между
  чтением и записью. Это явное «здесь другие могут вмешаться».
- **Вывод tz не копит.** `console.log` вокруг тяжёлой работы делает её последовательной; нужен
  параллельный расчёт — собрать строки и напечатать после.
- **Порядок ввода-вывода, написанный программистом, tz не меняет:** его видно снаружи (другая
  программа может смотреть на каталог).
- **Компилятор не уверен** (не знает, что трогает функция) — по очереди. Программа компилируется
  целиком, поэтому обычно он видит все вызовы.

## 3. Порядок

Гарантия: **результат — такой, какой мог бы выдать node**.

```ts
async function work(n: int) {
  const r = await heavy(n)       // расчёт без ввода-вывода
  console.log("готово", n)
  return r
}
await Promise.all([work(1), work(2), work(3)])
```

- **Где у node порядок жёсткий** (расчёты без ввода-вывода, как здесь), куски с общими данными
  идут в порядке node: всегда «готово 1», «готово 2», «готово 3», даже если `heavy(2)` кончился
  раньше. Сами `heavy` идут параллельно, ждут только короткие участки с общими данными.
- **Где порядок в node зависит от времени** — файлы, сеть, таймеры, запросы к серверу, — tz
  выбирает любой порядок, который мог случиться и в node. Здесь параллельность ничем не
  ограничена, кроме общих данных.
- Ошибку в программе без ввода-вывода, которая случилась один раз, можно повторить: результат
  на каждом запуске одинаковый.

## 4. Точность анализа

Сначала компилятор различает:
- разные поля одного объекта (`stats.read++` и `stats.converted++`);
- объекты, которые каждая задача создаёт сама;
- объекты, которые библиотека даёт одному вызову: `request` и `client` у обработчика сервера, и
  то, что из них получено полями и методами библиотеки (`request.headers`, `request.respond()`
  у `tz:http2`). Они свои у вызова, пока не уходят (раздел 8, «Сервер»);
- объекты классов программы, которые вызов делает сам или получает своими (4 ноября): `this`
  метода — свой, если свой получатель; поля своего объекта — свои; присваивания в конструкторе —
  начальные значения, а не изменение. Синхронное замыкание, которое вызов отдаёт своим помощникам
  и которое никуда не уходит, своих объектов не делает общими, а помощник, который зовёт
  полученное замыкание, несёт действия только этого замыкания. Общим объект становится, когда
  уходит: `this` в массиве модуля, общий массив в поле (тогда поле общее у всех объектов
  класса), замыкание у задачи, которую никто не ждёт. Тест — `run/parallel_classes`;
- свою ячейку массива: `results[i] = ...` внутри `map((f, i) => ...)`, если длина массива не
  меняется.

Чего при компиляции не видно — один объект дважды в общем массиве (`[a, a]`), ключи `Map`,
известные только при выполнении, — то идёт по очереди. Позже это можно проверять при выполнении:
замок на каждом общем объекте или ключе `Map` (разные — параллельно, одинаковые — по очереди).
Цена — атомарная операция при обращении и только у объектов, которые параллельные задачи делят
на деле; для `Map` — многопоточная реализация. Её программист уже может выбрать сам —
`ConcurrentMap` (раздел 9).

Точность анализа меняет только скорость, не результат: программы от уточнений не меняются,
только ускоряются.

- **Задача начинается с места вызова** (4 ноября). Обработчик сервера, который создан после
  настройки, ждущей только на одном пути (`if (db) await connect()` и потом `listen`), раньше
  считался созданным «в начале куска», и записи настройки шли по очереди с каждым запросом.
  Теперь продолжения куска, которые начинаются в операторах до вызова, не считаются идущими
  после него. Тест — `run/parallel_after_setup`.
- **Обратный вызов внутри многократной задачи — тоже многократный** (4 ноября). `setImmediate`,
  функция в `Pool.use` и другие обратные вызовы внутри обработчика сервера идут по разу на запрос,
  то есть одновременно; раньше анализ считал их однократными, и общий счётчик в таком вызове
  менялся из нескольких потоков без очереди. Тест — `run/parallel_handler_callback`.

## 5. Подсказки

Это подсказки, а не ошибки: код корректен, просто медленнее, чем мог бы быть.

- В редакторе: подчёркнут участок, из-за которого куски идут по очереди («по очереди с
  другими `convert`: все пишут в `cache`», переход ко второму месту по клику); у `Promise.all`
  — пометка «параллельно» или «по очереди (`cache`)»; над функцией — с чем она идёт
  параллельно.
- `tz build --explain-parallel` — то же текстом; вывод в JSON для инструментов. Анализ сразу
  выдаёт решения в структурированном виде, редактор потом просто читает готовое.
- Профиль при выполнении: сколько задачи реально ждали друг друга — чтобы подсвечивать то, что
  действительно тормозит.
- **Долгие места без `await`** (1.11). Пока кусок считает без `await`, другие куски его потока
  ждут. Компилятор подсказывает там, где количество работы зависит от данных, а предела в коде
  нет: «how many times this loop runs depends on data…». Подсказка видна в редакторе и в
  `tz build --hints`; обычная сборка её не печатает. Пометок не нужно: предел, написанный обычным
  кодом, и есть «я знаю».
  - Предел признаётся тем же анализом, что доказывает индексы и переполнения: цикл со счётчиком
    и постоянным шагом к ограниченному пределу (константа или проверка выше), `for-of` по
    коллекции с известной длиной (литерал, `.slice(0, N)`, проверка `length` выше). Предел должен
    быть меньше ~10⁹ проходов. Всё прочее (`for-of` по входным данным, обход списка по `next`,
    `while` по времени) — подсказка. Значения учитываются по всем вызовам функции: если все они
    передают ограниченное, подсказки нет.
  - Хвостовая рекурсия — тот же цикл (хвостовые вызовы в tz — переходы). Если один параметр
    меняется на постоянный шаг и рекурсия останавливается на проверке, подсказка у вызова, который
    передаёт неограниченное начало («how deep the tail recursion of 'down' goes depends on this
    argument»). Если такого параметра нет (рекурсия по `next`) — у самого хвостового вызова.
  - Без подсказок: циклы с `await` внутри, генераторы, циклы, условие которых читает ввод
    (`readLine`, синхронные `fs`), блокирующие вызовы (`readFileSync`, `execSync`), нехвостовая
    рекурсия (цикл по данным внутри неё получит подсказку сам), колбэки `forEach` / `map` /
    `reduce`. В коде библиотек подсказок не видно.
  - Только подсказка, код не меняется. Отпускать перед таким местом гири Pendulum (готовые ответы
    потока) пробовали: соседи получали ответы через 0–1 мс вместо ~2 мс у сторожа, но короткий
    цикл по данным есть почти в каждом обработчике, и пачки отправки рассыпались: h2c с циклом по
    `user-agent` — 0,34 млн запросов в секунду вместо 1,74 млн. Решено 1.11: взмаха нет, ждущих
    соседей выручает сторож. Тест — `run/long_loops` (и `hints/long_loops`: `tz build --hints`).

## 6. `Promise`, которого никто не ждёт

```ts
save("Ann")              // ошибка, подсказка: await save("Ann") или void save("Ann")
void save("Ann")         // ок — явно «запустить и не ждать»
const p = save("Ann")    // ок, дождёмся позже
await p

names.forEach(async n => { await save(n) })
// ошибка: forEach выбрасывает Promise из колбэка, функция закончится раньше, чем всё сохранится;
// подсказка: for (const n of names) await save(n) или await Promise.all(names.map(n => save(n)))
```

Так же, как забытый `Result` ([errors.md](errors.md)). В node такой `Promise` выполняется сам по
себе, а если бросит — программа падает.

`void` над `Promise<Result<...>>` — тоже ошибка: `Err` пропал бы молча. Задача, которую не ждут,
разбирает ошибку сама, и колбэк с `Result` нельзя передать туда, где ждут `() => void`
(слушатель, таймер, `forEach`) — [errors.md](errors.md), раздел 4:

```ts
void save("Ann")                     // ошибка, если save возвращает Promise<Result<...>>

async function saveOrLog(name: string) {
  const r = await save(name)
  if (r.isErr()) console.error(r.error)
}
void saveOrLog("Ann")                // ок: Promise<void>
```

## 7. Как в node

- Async-функция при вызове выполняется сразу, до первого `await`.
- `Promise`: `new Promise((resolve) => ...)`, `then`, `Promise.all` / `race` / `resolve` /
  `withResolvers`. Объекты со своим методом `then` `await` не разворачивает — только настоящий
  `Promise`: tz не вызывает код программиста неявно.
- **`Promise` не отклоняется** ([errors.md](errors.md), раздел 4). Операция, которая может не
  получиться, отдаёт `Promise<Result<T, E>>`; методов `Result` у `Promise` нет — сначала `await`.
  Уходят `reject` (у `new Promise` и `withResolvers`), `.catch`, `.finally`, `Promise.reject`,
  `allSettled`, `any`. Несколько сразу: `Promise.all` отдаёт каждый `Result` отдельно,
  `Result.combine(await Promise.all(ps))` — все значения или первая ошибка.
- Лишний `return await x` в `async`-функции — ошибка: `async`-функция и так дождётся `Promise`.
- Таймеры: `setTimeout`, `setInterval`, `clearTimeout`, `clearInterval`, `setImmediate`;
  `await setTimeout(100)` из `"node:timers/promises"` — пауза. `setInterval` подчиняется правилам
  подписки: метод объекта или стрелка с одним объектом — интервал останавливается, когда объект
  освобождён ([events.md](events.md), раздел 7).
- `await` на верхнем уровне модуля — как в ES-модулях. Программа завершается, когда не осталось
  задач, таймеров и ожидающего ввода-вывода.
- Не пойманных ошибок в задачах нет: `Result` нельзя выбросить (раздел 6).
- Отмены нет: `AbortController` и `AbortSignal` убраны 28 октября — громоздкий костыль, который в
  сообществе не любят. Ожидание идёт до конца; время запроса `fetch` ограничивает опция `timeout`
  в миллисекундах (`Err` с кодом `"TIMEOUT_ERR"`, [net.md](net.md)), сервер останавливает
  `listening.stop()`. `Promise.race` не отменяет проигравших, но снимает с них свои ожидания:
  тысяча гонок с одним долгим `Promise` не копит в нём тысячу записей.
- `node:worker_threads` нет: параллельность и так есть.

## 8. Рантайм

- Пул рабочих потоков — по одному на ядро. `TZ_THREADS=N` задаёт число потоков вместе с главным.
  Сервер, принявший первое соединение, добавляет пулу ещё один поток: соединения (и с TLS тоже)
  ведут потоки пула, а главный поток сервера в это время ждёт, так что работают все N ядер. До
  2 ноября их было N − 1: на двух ядрах сервер шёл как на одном, а HTTPS целиком шёл через главный
  поток ([net.md](net.md), раздел 6, «По ядрам»).
- **Как куски идут параллельно.** Порядок node держит главный поток: цикл событий, очередь
  микрозадач, таймеры. Кусок после `await`, который может идти одновременно с другими, рантайм
  отдаёт свободному потоку, как только тот встал в очередь за тем, что главный поток выполняет.
  Поток выполняет кусок заранее, пока тот трогает только свои данные и то, что никто не меняет, и
  перед первым обращением к общим данным ждёт своей очереди. Когда главный поток доходит до куска,
  он отдаёт ему очередь и ждёт, пока кусок закончится в своём потоке. Так результат — порядок node,
  а расчёты до первого общего обращения идут на всех ядрах.
- Кусок, который один ждёт чтения файла (`node:fs/promises`), уходит в поток, как только файл
  прочитан, а событие чтения цикл проводит, когда кусок дойдёт до общих данных: время событий
  ввода-вывода в node тоже решает система.
  - Чтение, которое начал кусок в пуле, уходит потокам ввода-вывода, когда кусок закончится
    (1.11). Иначе главный поток мог выполнить `Promise` чтения, пока кусок на него только
    подписывался, и подписка терялась: программа кончалась с «unsettled top-level await» (1–2
    раза на 200 запусков `run/group_race` с `TZ_PARALLEL_PROVOKE` и `TZ_CHECK_LEAKS`). Кусок
    между `await` короткий, так что чтение начинается почти тогда же.
  - Так же с 4 ноября — операции сокетов `tz:socket` в пуле и ожидание в `Pool`: операция
    стартует, а ожидание регистрируется, когда кусок закончится (в потоке пула — после задачи; в
    главном потоке и у куска, который держал очередь, — отдельной микрозадачей после всего, что
    кусок туда поставил). Раньше продолжение запроса могло пойти в другом потоке, пока прежний
    кусок того же запроса ещё шёл, и счётчики ссылок общих для них объектов портились: мини-Nest
    `/db` падал раз в три запуска, с `TZ_CHECK_LEAKS` — за секунды («below zero»).
  - Сопрограмма запоминает, откуда продолжать, до вызова `tz_async_await`, а не после
    (`llvm.coro.save` перед вызовом, 4 ноября). Иначе продолжение, которое другой поток запустил
    в этот промежуток, шло не с того места.
- **Объекты, которые становятся общими по ходу** (4 ноября). Две ошибки компилятора оставляли
  объект в общих данных своим, и его счётчик ссылок меняли несколько потоков без атомарных
  операций (двойное освобождение, access violation):
  - `push` и `unshift`, встроенные в программу, не делали общим объект, добавленный в общий
    массив (функция рантайма это делала). Так свежие объекты `Pool` попадали в общий список
    свободных: падало в начале нагрузки, примерно раз в три запуска.
  - Литерал, массив, кортеж, окружение замыкания: запись поля с общим объектом сразу делала
    новый объект общим, а поля после него ещё не были записаны и общими не становились. Так
    маршруты мини-Nest (`{ route, segments, controller }`) держали свои массивы сегментов, и `/db`
    падал раз в ~12 запусков. Теперь сначала записываются все поля, потом объект связывается с
    группой.
- **Сервер** ([net.md](net.md)). События соединений сервера приходят не в главный поток, а в
  потоки пула (у них свой порт IOCP). Поток, который прочитал заголовок запроса, сам выполняет
  кусок, ждавший его: `Request`, обработчик, ответ, ожидание следующего запроса. Пока кусок не
  трогает общих данных, главный поток о нём не знает; тронул — ждёт очереди, и событие проводится
  тогда, как выше. Функции рантайма для соединения очереди не ждут: соединение трогает только его
  задача, под замком соединения. Микрозадачи такого куска (`await` готового значения, `Promise`,
  который видит только он) выполняются в том же потоке после него. «Hello, World!» — 314 тыс.
  запросов в секунду против 239 тыс. у Go. Обработчик, который трогает общие данные, идёт в
  порядке node через главный поток (92 тыс.).
  - **Первый запрос соединения — тоже в пуле** (1.11). Если запрос уже лежал в сокете, когда
    главный поток начал читать (клиент прислал его вместе с приветствием HTTP/2 или сразу после
    подключения), главный не разбирает его сам, а отдаёт потоку пула — как будто данные пришли
    чуть позже. Иначе долгие обработчики первых запросов шли на главном по одному. Замер: 16
    новых соединений h2c, на каждом сразу запрос со 100 мс расчёта — все ответы за 106 мс (было
    106–1609 мс по одному); 64 таких — за 110–310 мс. Тест — `run/http2_fresh_slow`.
- **Свои объекты вызова** (31.10). `request` и `client`, которые сервер даёт одному вызову
  обработчика, и всё, что из них получено полями и методами библиотеки, принадлежат этому вызову:
  их чтение и запись другим вызовам не мешают, а счётчики ссылок у них остаются простыми, хотя
  куски обработчика идут в разных потоках. Так же — у функции, которой их передали: анализ
  смотрит каждый вызов отдельно, и помощник, которому один обработчик даёт свой `request`, а
  другой код — общий, первому не мешает. Свои они, пока не уходят: в глобальную переменную,
  поле, массив, `Map`, в функцию без `await` (её куски идут рядом с обработчиком), в таймер, в
  замыкание или в функцию библиотеки, — тогда объект общий и кусок, который его трогает, идёт по
  очереди. Тест — `run/parallel_owned`.
  - Замер (HTTP/1.1, 256 соединений): `request.headers.get(…)` в синхронном обработчике —
    92 тыс. → 300 тыс., `await request.text()` — 85 тыс. → 305 тыс., как «Hello, World!».
  - Функция с кусками в других потоках делает свои аргументы и `this` общими при входе. Если
    её `Promise` ждут сразу (`await f(x)` или `const p = f(x)` и следующей строкой
    `await p`), она идёт в задаче вызывающего и ничего общим не делает.
  - **Объекты, которые вызов делает сам** (2.11), — тоже его: `new`, литерал, результат функции
    библиотеки и её статического метода с простыми аргументами (`URL.parse(request.url)`),
    результат функции программы, которая всегда отдаёт новый объект (`const params =
    match(...)`, где `match` строит и возвращает `new Map`). Своими они остаются:
    - при `return` — в функции, которая их сделала, они свои до возврата, а вызывающий получает
      новый объект;
    - в литерале типа, объявленного в программе (`const context: Context = { request, params,
      query }`): поле такого объекта своё, если каждый литерал этого типа, который может стать
      своим, кладёт в это поле своё и поле не меняют присваиванием. Тип сравнивается по
      строению: два `type` с одинаковыми полями — один тип;
    - при передаче в функцию — прямо, методом, через значение функции (роутер,
      `route.call(controller, context)`) и `method.call(controller, context)`. И когда
      синхронная функция отдаёт `Promise` async-функции (`(request) => this.handle(request)`),
      если её саму сразу ждут, отдают через `return` или её зовёт сервер.
  - Общими они становятся так же, как `request`: в глобальной переменной, в поле общего объекта,
    в массиве, в замыкании, в функции библиотеки, в функции, которая идёт рядом с вызовом (`const
    later = start(x)` без немедленного `await`). Литерал, который ушёл в общее место, полей своего
    типа не портит: через свои ссылки его уже никто не прочтёт. Тест — `run/parallel_own_objects`.
  - Замер (HTTP/1.1, 128 соединений, копия мини-Nest из typezero-test-app без пишущих маршрутов,
    с `ctx.params.get` и `ctx.query.get`): на 8 ядрах 42 тыс. → 281 тыс. запросов в секунду
    (`/health`), 275 тыс. (`/notes/:id`), 177 тыс. (`/notes`, JSON 20 заметок) — как «Hello,
    World!». С пишущими маршрутами — по-прежнему ~43 тыс.: вызов-диспетчер несёт запись в общий
    `Map` заметок.
  - Async-функцию, которую синхронная функция зовёт без `await`, анализ считает идущей в задаче
    вызывающего, но аргументы она при входе по-прежнему делает общими: вызывающий освобождает
    свои ссылки на них, когда её куски уже могут идти в другом потоке.
- **`return f()` в async-функции** (2.11). Промис, который async-функция отдаёт без `await` (так
  и надо писать: `return await` — ошибка сборки), принимается в потоке куска, как `await`, с тем
  же числом тактов, что в node (тест `run/async_return_promise`). Раньше принятие всегда ждало
  очереди главного потока: обработчик, который вызывает async-функцию и отдаёт её результат,
  шёл на одном ядре — 44 тыс. запросов в секунду на 8 ядрах вместо 286 тыс. (HTTP/1.1, замер
  на копии мини-Nest из typezero-test-app).
  - **Гонка (4 ноября).** Продолжение, которое следует за чужим `Promise`, задача меняла до
    своей очереди, хотя главный поток уже держал его в очереди микрозадач (оно переехало туда из
    очереди потока, когда задача ждала очереди, и пул раздал его как кусок). Главный поток потом
    запускал его без исходного `Promise` — access violation на первом же запросе мини-Nest с
    `Pool` (3 из 10 запусков), на тесте — почти всегда. Теперь до своей очереди меняется только
    ранний кусок. Тест — `run/sync_pool_return`.
- **Методы под декоратором, вызванные через значение** (2.11). Роутер на декораторах хранит
  `descriptor.value` и зовёт его (`method.call(controller, ...)`); анализ теперь видит тела этих
  методов в каждом таком вызове. Раньше не видел, и обработчики, которые читают и пишут общий
  `Map`, шли параллельно: под смешанной нагрузкой (GET и POST разом) программа падала с
  `access violation`. Тест — `run/decorators_dispatch`. Вызов через одно значение (роутер)
  несёт действия всех методов, которые туда могут попасть: если хоть один пишет общие данные,
  вызов идёт по очереди для всех.
- **Ожидание очереди — у самого обращения** (2.11). Если общие данные трогает вызванная функция
  программы, кусок ждёт очереди не перед вызовом, а внутри неё — в начале оператора, где
  обращение. Так делается, только если каждый кусок, который выполняет эту функцию, сам ждёт на
  этом операторе, в операторе нет `await` и путь не идёт через код библиотеки (функцию, которую
  зовёт библиотека, — `emit`, `update` у `ConcurrentMap`, — кусок ждёт до вызова). Иначе — как
  раньше, перед вызовом. `--explain-parallel` печатает «waits for its turn inside: …». У мини-Nest
  ожидание ушло из начала запроса в методы хранилища заметок, но скорости это не дало: кусок,
  который почти всегда просит очередь, рантайм выполняет в главном потоке (ниже, «короткие куски»),
  а передача очереди через главный поток дороже всего запроса.
- **Ошибки `JSON.parse` и `JSON.stringify` в параллельных кусках** (2.11). Функцию, которая
  строит объект ошибки, рантайм держал в одной переменной на всю программу, и каждый вызов её
  перезаписывал: два потока сбивали друг другу ошибки — паника «a Json error with nothing to take
  it» или `access violation` (мини-Nest под `GET` вместе с `POST` с неверным JSON падал за
  секунду). Теперь она у каждого потока своя. Тест — `run/json_errors_parallel` (под
  `TZ_PARALLEL_STRESS` падал 5 раз из 5).
- **Pendulum: вывод тактами** (31.10–1.11). Ответ HTTP/2 уходит в сокет не сразу: соединение
  кладёт «гирю» в список потока, и поток отправляет всё накопленное разом — в конце куска, перед
  ожиданием и после завершения ввода-вывода ([structure.md](structure.md), «Pendulum»). Одна
  отправка на соединение вместо отправки на каждый `respond` / `write` / `end`.
  - Замер (h2c, 32 соединения по 8 запросов): «Hello, World!» — 1,61–1,75 млн запросов в секунду
    (было 376 тыс.; Go — 221–228 тыс., Rust hyper — 716–758 тыс.), `await request.text()` и
    `tz:http2` с `write` и `end` — 1,54–1,68 млн. HTTP/1.1 — как было (~295 тыс.).
  - Сосед ждёт не дольше ~2 мс. Если после готового ответа поток долго считает без `await` (другой
    запрос того же куска), гири забирает сторож — отдельный поток, который просыпается к сроку
    (гиря старше 1 мс) и отправляет за занятый поток. Замер: на одном соединении 7 быстрых
    запросов и один со 100 мс расчёта — быстрые приходят через 1,7–1,8 мс (без сторожа — через
    100 мс), под полной нагрузкой на другие соединения — через 1,8–3,1 мс; скорость та же. Без гирь
    сторож спит: 5 пробуждений за 11 с простоя. Тест — `run/http2_slow_neighbor`.
  - **Сторож раздаёт и сами запросы** (1.11). Запросы HTTP/2, пришедшие одним пакетом, читавший
    поток выполняет по очереди. Если один считает долго, остальные (их обработчики ещё не начаты)
    сторож через ~1 мс отдаёт свободным потокам. Замер (одно соединение, один пакет): `/slow` и
    7 быстрых — быстрые через 1–2 мс (было 100 мс), 4 медленных — 101–105 мс (было по одному).
    Переносит только то, что библиотека отметила как независимое ([structure.md](structure.md),
    «Сторож раздаёт куски»). Тест — `run/http2_fast_after_slow`. Скорость та же (A/B ±1%).
- Отдать кусок потоку стоит микросекунды, поэтому каждый `await` учится, сколько его куски идут до
  первого общего обращения, и короткие (до 30 мкс) выполняет в главном потоке.
  - Ещё он учится, просят ли его ранние куски очередь сразу. Если почти всегда да, их перестают
    выполнять в пуле. Кусок, который успел посчитать дольше 30 мкс, сбрасывает этот счёт (1.11).
    Без этого клиенты, закрывавшие соединения HTTP/2 во время ответа, через несколько десятков
    соединений переводили сервер на главный поток: 64 запроса по 100 мс шли 6,4 с вместо 0,21 с.
- Программа без таких кусков собирается с рантаймом одного потока и ничего за потоки не платит.
- Ожидание ввода-вывода — IOCP в Windows, epoll / io_uring в Linux. Пока задача ждёт, её поток
  выполняет другие.
- **Вытеснение: долгий кусок не задерживает остальных.** Кусок между `await` занимает поток до
  конца — сохранить его посреди работы негде, своего стека у задачи нет. Поэтому за потоками
  следит рантайм. Если все потоки пула дольше ~10 мс заняты каждый одним куском (долгий расчёт или
  синхронный ввод-вывод вроде `readFileSync`), а другие куски ждут, рантайм берёт запасной поток
  (не больше, чем потоков в пуле), и ОС делит ядра между ними.
  - Так быстрые запросы не ждут тяжёлых. В Go для этого долгую горутину прерывают примерно
    через 10 мс.
  - Запасной поток дешёвый: создать — 40 мкс, разбудить — 2 мкс, ~17 КБ памяти (мерили для
    фонового освобождения). Число запасных потоков ограничено.
  - Правило D и порядок node не страдают: долгий кусок для программы по-прежнему выполняется
    целиком, а задачи, которым нужны его данные, ждут, как и раньше.
- Async-функции превращаются в конечные автоматы средствами LLVM (те же проходы, что у корутин
  C++20).
- Счётчики ссылок обычные (не атомарные), пока объект виден одному потоку. Общим (с атомарным
  счётчиком) объект становится, когда его может достать другой поток: его кладут в глобальную
  переменную, которую видят функции, или в общий объект, передают async-функции, чьи куски идут
  заранее, выполняют им общий `Promise`. Общим тогда становится и всё, что в нём лежит;
  компилятор ставит эти места в коде, а рантайм обходит объект по описанию его полей. Группу
  объектов в циклах ([objects.md](objects.md)), которую видит один поток, он и меняет без замка; у
  общей группы счётчики (группы и членов) атомарные, тоже без замка, а замок на всю программу
  берётся, только когда ссылка связывает две разные группы (слияние) и когда из общей группы
  уходит освобождённый член (его вынимают из кольца членов).
  - **Член, которого записали в общую группу, вливается в неё до того, как ссылку увидят другие
    потоки** (3.11). Иначе его прежний вожак успел бы побыть вожаком общей группы, а такого члена
    нельзя освободить отдельно: другой поток мог прочитать его как вожака и ещё не прибавить к его
    счётчику. Раньше барьер записи делал значение общим, потом шла запись, потом слияние — и
    каждый кусок данных, прочитанный из сокета пула PostgreSQL, оставался в группе сокета до его
    закрытия (~150 байт на кусок).
  - **Значение `Promise`, которого не видят другие потоки, остаётся необщим** (2.11). Такой
    `Promise` ждёт та же задача (`await f()`, `return f()`), и её куски идут по очереди, как со
    своими объектами вызова. Раньше значение любого `Promise` становилось общим, а запись его в
    `Promise` — членом группы — шла через замок слияния на всю программу: мини-Nest из
    typezero-test-app брал его 3–4 раза на запрос и по HTTP/2 упирался в ~1,05 млн запросов в
    секунду с 8 потоков, а на всей машине (32 потока) падал до 460 тыс. — потоки стояли в
    очереди за замком. Стало (h2c, копия без пишущих маршрутов): 8 потоков 1,05 → 1,19 млн, 16 —
    1,08 → 1,48 млн, вся машина — 460 тыс. → 1,09 млн. Если такой `Promise` потом станет общим,
    его значение публикуется вместе с ним.
  - `WeakRef` общий — общий и объект, на который он указывает (1.11). Иначе потоки, читающие
    через `deref`, меняли бы простой счётчик: утечки и падения. `deref` в другом потоке, пока
    группа умирает, даёт `undefined`, а не оживляет её: счётчик растёт сравнением с обменом,
    только пока он не ноль. Обе гонки нашёл режим `TZ_PARALLEL_PROVOKE=1` (рантайм спит 1 мс в
    окнах гонок, [structure.md](structure.md)). Тест — `run/group_race`.
- У каждого потока своя куча; блок, освобождённый чужим потоком, уходит в атомарный список кучи
  владельца, и тот забирает его, когда ему не хватит места.
- Освобождение больших групп объектов в фоне отложено ([objects.md](objects.md), шаг 10): пока
  группа освобождается сразу, в потоке, где умерла.

## 9. `ConcurrentMap`

Общий `Map`, у которого каждое действие целое само по себе: внутри замок «один пишет или много
читают». Очередь node для него не нужна: задачи, которые его трогают, идут параллельно, даже
когда кто-то пишет.

```ts
import { ConcurrentMap } from "tz:sync"

const notes = new ConcurrentMap<string, Note>()
notes.set(id, note)
const note = notes.get(id)                                  // Note | undefined
notes.update(id, (old) => ({ ...old, title }))              // прочитал и записал за раз
const hits = counts.getOrSet(path, () => 0)                 // есть — отдаёт, нет — кладёт
for (const [id, note] of notes.entries()) { ... }           // снимок: новый массив
```

Методы: `size()`, `get`, `has`, `set`, `delete`, `clear`, `update(key, change)` (ключа нет —
ничего не делает и отдаёт `undefined`), `getOrSet(key, make)`, снимки `keys()`, `values()`,
`entries()`.

- **Порядок.** Внутри задачи — как написано. Между задачами — кто первый успел, а не порядок
  node: `GET` и `DELETE` одной заметки, пришедшие почти одновременно, могут разойтись в любую
  сторону. Каждое действие при этом целое. Программист выбирает это сам, когда берёт
  `ConcurrentMap` вместо `Map`; обычный `Map` по-прежнему идёт в порядке node.
- **«Прочитал, потом записал» двумя действиями** (`get`, потом `set`) — между ними другой запрос
  может успеть, и одно обновление пропадёт. Одним действием — `update` или `getOrSet`.
- **Функция в `update` и `getOrSet` выполняется под замком карты:**
  - она не ждёт: `async`-функция — ошибка типа (`(V) => Promise<V>` не `(V) => V`);
  - она не трогает `ConcurrentMap` — ни эту, ни другую: два потока, держащие по замку и ждущие
    чужой, встали бы навсегда. Программа вместо этого останавливается паникой с местом вызова
    (тест `run/sync_nested`);
  - общие данные трогать можно: тогда кусок ждёт своей очереди до вызова `update`, а не под
    замком.
- **Значения — обычные объекты.** Менять их на месте можно, но такие изменения анализ видит как
  любые общие данные и ставит в порядок node; быстрее — заменять значение (`update`).
- **Обход — снимком.** `for (... of map)` — ошибка: пока идёт цикл, карту меняют другие.
  `keys()`, `values()`, `entries()` копируют всё разом под замком.
- **Как сделано.** `library/core/sync.tz`: обычный `Map` и замок SRWLOCK
  (`runtime/library/sync`). Анализ не считает действия `ConcurrentMap` общими данными, а функцию
  из `update` и `getOrSet` — выполняемой на месте (`LibraryEffects`). Замок один на карту;
  разбить на части по ключам — если он упрётся (пока не упирается: замер ниже).
- **Замер** (2.11, HTTP/1.1, 8 ядер, 128 соединений, копия мини-Nest из typezero-test-app со всеми
  маршрутами, заметки в `ConcurrentMap`): `/health` 43 тыс. → 280 тыс. запросов в секунду,
  `/notes/:id` 42 → 270 тыс., `/notes` (JSON 20 заметок) 24 → 180 тыс.; занято 7,6 ядра вместо
  одного. `GET` вместе с `POST` разом: 82 тыс. и 1,2 тыс. в секунду (было 24 тыс. и 0,4 тыс.;
  `POST` упирается в запись файла заметок целиком). По h2c (32 соединения по 8 запросов,
  `/health`): 8 потоков — 142 тыс. → 1,20–1,22 млн, 16 потоков — 143 тыс. → 1,47–1,48 млн,
  вся машина — 160 тыс. → 1,05–1,11 млн; столько же, сколько у копии без пишущих маршрутов
  (1,22 / 1,50 / 1,02–1,08 млн), то есть один замок карты не упирается. `/notes/:id` на 16
  потоках — 1,40 млн, `/notes` — 369 тыс. (JSON). Тест — `run/sync_concurrent_map`.

## 10. `AsyncLocalStorage`

Решено и сделано 3 ноября. Из `node:async_hooks` есть только `AsyncLocalStorage`; примеры
правил — `tmp/design/async-local-storage.tz`.

```ts
import { AsyncLocalStorage } from "node:async_hooks"

type RequestContext = { requestId: string; user?: string }
export const requestContext = new AsyncLocalStorage<RequestContext>()

const server = new Server(options, (request) =>
  requestContext.run({ requestId: randomUUID() }, () => route(request)))

function log(message: string) {
  const id = requestContext.getStore()?.requestId ?? "-"     // в любой функции, после любых await
  console.log(`[${id}] ${message}`)
}
```

- **Методы** — `run(store, fn)` (вызывает `fn` и отдаёт её результат) и `getStore()`. Тип
  `getStore()` — `T | undefined`, как в node: вне `run` хранилища нет. Доказывать «здесь всегда
  внутри `run`» и давать `T` — позже, вместе с шагом 15 [events.md](events.md): обоим нужно
  следить за функциями-значениями по всей программе ещё при проверке.
- **Чего нет:** `enterWith` (ставит хранилище «до конца текущего кода» и во всё, что тот
  запустит, — граница не видна), `bind` и `snapshot` (функция, которая носит хранилище всегда, —
  та же утечка, что у интервала), `disable` и `exit` (на практике не нужны), `AsyncResource`,
  `createHook` и остальное из `node:async_hooks`.
- **Что несёт хранилище** — как в node: `await`, `.then`, `setTimeout`, `setImmediate`,
  `queueMicrotask`, `process.nextTick` запоминают его, когда их создают. Слушатель события идёт с
  хранилищем того, кто вызвал `emit`: подписка его не запоминает, поэтому долгий эмиттер не держит
  хранилища подписчиков. Async-генератор после `yield` идёт с хранилищем того, кто вызвал `next()`.
- **Правила** (ошибки сборки, проверка — `ContextChecker` по всей программе):
  1. Хранилище (`new AsyncLocalStorage`) — только `const` на верхнем уровне модуля: все
     хранилища и все их `run` видны при сборке, а освобождать само хранилище не нужно.
  2. Значение для `run` — новый объект, написанный прямо в вызове: `run({ requestId }, ...)`,
     `run(new Trace(request), ...)`. Уже существующий объект мог бы попасть в два `run` сразу.
     Строки, числа и другие значения без ссылок — любые.
  3. Значение из `getStore()` нельзя сохранить вне `run`: в поле, массив, `Map`, переменную модуля
     или внешней функции, в новый объект, в функцию библиотеки, которая может его сохранить, и в
     функцию-значение, за которой компилятор не следит. Передать функции программы можно — тогда
     правило проверяется в ней; вернуть из функции — тоже (тогда её результат — то же значение).
     Копия полей — можно: `{ ...store }`, `store.requestId`. Печатать (`console.log`,
     `JSON.stringify`) — можно.
  4. `setInterval` и `setTimeout`, который перезапускает сам себя, хранилище не несут: они живут
     дольше `run`. Если их функция читает `getStore()` — сама или через функции, которые зовёт, —
     ошибка: нужное берут до `setInterval` и держат в объекте интервала
     ([events.md](events.md), раздел 7).
- **Рантайм.** У потока есть «текущее хранилище» — цепочка кадров `run` (кадр: хранилище,
  значение, внешний кадр). `run` ставит свой кадр на время `fn` и возвращает прежний. Ожидание и
  таймер запоминают текущий кадр (одна ссылка), а их продолжение, в каком бы потоке пула оно ни
  шло, ставит его на время своей работы и потом возвращает прежний. Кадр `run` общий (атомарный
  счётчик): его держат продолжения в разных потоках.
  - `await` и `.then` запоминают кадр в самой реакции (поле `context` у `TzReactor`), и делает это
    код программы, только если программа импортирует `node:async_hooks`: тогда и функция
    продолжения (`tz.async.resume`, обработчик `then`) ставит запомненный кадр. Остальные
    программы на `await` не делают ничего лишнего.
  - `setTimeout`, `setImmediate`, `queueMicrotask` и `nextTick` запоминают кадр в рантайме, когда
    их создают; `setInterval` и таймер с получателем — нет.
  - Очередь микрозадач, таймеры и ввод-вывод рантайм запускает с верхнего уровня, где текущего
    кадра нет, а каждая работа с кадром возвращает прежний. Поэтому продолжение без запомненного
    кадра идёт с пустым, и поток не покажет запросу B хранилище запроса A.
  - `run` — внутренняя функция библиотеки `withContext(frame, fn)`: компилятор ставит кадр, вызывает
    `fn` и возвращает прежний, так что `run` с функцией без результата (`void`) тоже работает.
- **Параллельность.** `run` и `getStore` анализ не считает общими данными, функция в `run`
  выполняется на месте. Само значение из `getStore()` — общий объект: чтение его полей идёт
  параллельно, запись (`store.user = ...`) — по очереди со всеми, кто его трогает. Что запись в
  значение своего запроса другим запросам не мешает, анализ пока не знает; правила 2 и 3 к этому
  готовят.
- **Цена** (замер 3 ноября, A/B с 54283f7). Программы без `AsyncLocalStorage`: `async_await`,
  `async_tasks`, `async_timers`, `async_parallel` и остальные — в пределах шума (±3%). Сервер
  «Hello» с `await` в обработчике (HTTP/1.1, 8 потоков, 128 соединений): 286–290 тыс. запросов в
  секунду до, 282–293 тыс. после; с `run({ requestId }, ...)` и `getStore()` на каждый запрос —
  289–293 тыс. Первый вариант, где каждый `await` любой программы читал текущее хранилище потока,
  стоил `async_await` 4–8%, проверка флага «хранилище включено» — тоже около 5%, поэтому запоминание
  перенесено в код программ, которые его используют.
- Тесты: `run/async_local_storage` (`// same-as-node`), `run/async_local_storage_server` (600
  запросов на потоках пула, каждый после `await`, таймера и `setImmediate` видит своё значение),
  `errors/async_local_storage`.

## 11. `Pool`

Решено 3 ноября, сделано 4 ноября. Пул объектов, которыми в каждый момент пользуется одна задача
и которые дорого создавать заново: соединения с базой, соединения со своим протоколом поверх
TCP, большие буферы, дочерние процессы. Примеры — `tmp/design/pool-plain.tz` и `tmp/design/pool.tz`.

```ts
import { Pool } from "tz:sync"

const database = new Pool<PgConnection, PgError>({
  max: 32,
  create: async () => PgConnection.open(options),     // Promise<Result<PgConnection, PgError>>
  alive: (connection) => !connection.isBroken(),       // мёртвое при возврате пул выбрасывает
})

async function select(sql: string): Promise<Result<Row[], PgError>> {
  return database.use(async (connection) => connection.query(sql))
}

const buffers = new Pool<Buffer>({                     // E = never: создание не ошибается
  max: 64,
  create: async () => ok(Buffer.alloc(1 << 20)),
  reset: (buffer) => buffer.fill(0),                   // почистить при возврате
})
const length = await buffers.use(async (buffer) => ok(buffer.length))
console.log(length.value)                              // Result<int, never>: без проверки
```

- **`use(fn)`** берёт свободный объект (последний возвращённый), иначе создаёт новый, пока их
  меньше `max`, иначе ждёт; вызывает `fn` и возвращает объект в пул, когда её `Promise`
  закончится. Забыть вернуть, вернуть дважды, пользоваться после возврата — нельзя по построению.
  `acquire` / `release` нет.
- **Только `async`:** `create` — `() => Promise<Result<T, E>>`, функция в `use` —
  `(item: T) => Promise<Result<R, F>>`, `use` отдаёт `Promise<Result<R, E | F>>`: ошибка
  создания и ошибка функции — в одном `Result`, различаются по `kind`. `E = never`, если создание
  не ошибается; у `Result<T, never>` поле `value` читается без проверки.
- **Ошибка `create`** — пул уменьшает счётчик и будит одного ждущего: тот пробует создать сам.
  **При возврате** — сначала `alive` (мёртвый — выбросить, разбудить ждущего), потом `reset`;
  ждущему объект отдаётся сразу, без очереди свободных. `stats()` — `{ total, idle, waiting }`.
- **Объект живёт только внутри `use`** (ошибки сборки, `PoolChecker` по всей программе — тот же
  обход, что у правила 3 `AsyncLocalStorage`, общий класс `HeldValueChecker`): его нельзя
  сохранить в переменную модуля или внешней функции, поле, массив, `Map`, новый объект, отдать
  функции библиотеки, которая может его сохранить, или функции-значению, за которой компилятор не
  следит; нельзя отдать таймеру функцию, которая его использует; нельзя `void` вызова, который
  его использует (`use` вернёт объект, не дождавшись); функция в `use` не может вернуть сам объект
  (`ok(connection)`). Можно — читать и менять поля, звать его методы (правило проверяется в них,
  `this` метода — тот же объект), передать функции программы (правило проверяется в ней),
  `await`, `Promise.all` над его вызовами. Те же правила — у параметра `alive` и `reset`.
- **Объект пула в хранилище `AsyncLocalStorage`** (4 ноября, для неявных транзакций базы, как
  `typeorm-transactional`; примеры — `tmp/design/pool-in-store.tz`):

  ```ts
  const transactions = new AsyncLocalStorage<{ connection: PgConnection }>()

  async function transaction<T, E>(fn: () => Promise<Result<T, E>>) {
    return pool.use(async (connection) => {
      ...
      const result = await transactions.run({ connection }, fn)   // можно
      ...
    })
  }

  async function query(q: SqlQuery) {
    const scope = transactions.getStore()                      // на любой глубине внутри run
    if (scope != undefined) return scope.connection.execute(q)
    return pool.use(async (connection) => connection.execute(q))
  }
  ```

  Объект можно положить в хранилище `run`, если хранилище — литерал прямо в вызове, а `run`
  ждут (`await` или `return`) внутри `use`. Тогда хранилище такого `AsyncLocalStorage` и объект
  пула в его поле живут по правилам объекта пула: их нельзя сохранить (поле, переменная модуля,
  массив, `Map`, копия `{ ...scope }`). В коде, до которого может дойти функция `run` (через
  параметр — до функций, которые ей передают, и дальше по вызовам), нельзя таймер (`setTimeout`,
  `setImmediate`, `queueMicrotask`, `process.nextTick`) и `void`-вызов с функцией, которая читает
  хранилище — сама или через вызовы: она пошла бы после `use`. Функцию, которую зовут и в
  транзакции, и вне её, проверка считает транзакционной. Ошибки: `run` без `await` или
  `return`, хранилище не литералом (`run(new Scope(connection), fn)`), сохранение, копия, таймер,
  `void`. Тесты: `run/sync_pool_store`, `errors/sync_pool_store`. Транзакция драйвера PostgreSQL
  typezero-test-app на этом — 1,3 мс против 4,5 мс со своим соединением на каждую (замер 4 ноября).
- **Параллельность.** Сам пул (кто свободен, кто ждёт) — под замком, как у `ConcurrentMap`:
  анализ не считает его действия общими данными. Функция в `use`, `create`, `alive` и `reset` —
  обратные вызовы библиотеки (своя задача на каждый вызов). Объект в функции `use` — **свой у
  вызова** (как `request` у обработчика), если каждый `create` пулов с таким типом объекта отдаёт
  новый объект (`ok(new X())`, литерал, функция программы, которая всегда отдаёт новый): тогда
  его поля меняются без очереди. Если `create` отдаёт существующий объект — объект общий и куски,
  которые его трогают, идут по очереди. В `--explain-parallel` функция в `use` с полями своего
  объекта — `parallel` (тест `run/sync_pool_server`).
- **Рантайм.** `use` — код библиотеки на tz: замок `syncGuard` (SRWLOCK), список свободных,
  ждущие — объекты рантайма (`syncWaiter` / `syncWait` / `syncWake`), а не
  `Promise.withResolvers`: общий `Promise` будил ждущего через главный поток. Ожидание
  регистрируется в конце куска (раздел 8); будит его поток того, кто вернул объект, а если тот не
  ранний кусок — поток пула. Продолжения после `await` внутри `use` помечены `ahead(...)`, иначе
  каждое шло бы через главный поток.
- **Что уже дал** (замер 4 ноября, HTTP/1.1, 8 ядер, 64 соединения): мини-Nest из
  typezero-test-app с базой — `/health` 46 тыс. → 258 тыс. запросов в секунду, `/notes` →
  244 тыс. Все маршруты идут через один диспетчер (вызов через значение несёт действия всех
  методов), а прежний пул на полях программы (`idle`, `waiters`, `total`) писал общие данные — и
  каждый запрос, даже без базы, шёл по очереди. С `Pool` его действия не общие.
- **`/db` на всех ядрах** (4 ноября). Сначала мини-Nest `/db` (PostgreSQL, `select 1`) шёл на
  одном ядре: 19,7 тыс. запросов в секунду на 8 ядрах. Две причины и что сделано:
  1. Своё у вызова анализ знал только для литералов и объектов библиотеки: у класса программы
     получатель метода считался ушедшим, поля — не своими. Теперь объекты классов программы —
     свои у вызова (раздел 4).
  2. Чтение клиентского сокета `node:net` приходит в главный поток. Соединение PostgreSQL в
     typezero-test-app теперь на `tz:socket`: его сокеты ведут потоки пула (у них свой порт
     IOCP), продолжения после `accept`, `connect`, `send`, `receive` идут заранее, операция
     стартует в конце куска (раздел 8). `node:net` `Socket` по-прежнему идёт через главный поток.

  Замер (HTTP/1.1, 8 ядер, oha с 8 других ядер): `/db` — 140–141 тыс. запросов в секунду (пул 16
  соединений, 128 клиентов; пул 64, 32 клиента — столько же), на 1 ядре — 26–27,6 тыс. (было
  22,8). Go — 121 тыс., node на 8 процессах — 136 тыс. `/health` — 276–279 тыс. Под нагрузкой,
  20 запусков по 3 секунды, — без падений (до исправлений раздела 8 — раз в 3–12 запусков).
- **Отложено:** срок ожидания (`wait`, ошибка `PoolWaitError` в `E`) — тип ошибки не может
  зависеть от того, передали ли `wait`; закрыть пул (`close` / `drain`) — нужен способ закрыть
  объект (`destroy` в опциях).
- Тесты: `run/sync_pool` (поведение), `run/sync_pool_server` (400 запросов, свой объект в
  каждом, `.explain`), `run/sync_pool_return`, `errors/sync_pool`.

## 12. Отложено

- **Общие объекты** — чтобы сотни обработчиков запросов, которые трогают один `cache`, шли
  параллельно: каждый вызов метода берёт замок объекта только на время вызова. Обсуждали
  декоратор `@shared class Cache` (синтаксис TS) и правила: поля закрыты, в методах нет `await`,
  наружу — только неизменяемые значения или другие общие объекты.
- **`Mutex` / `Semaphore`** — атомарность через `await`. Пока — как в JS: между `await` другие
  задачи могут вмешаться. Обсуждали встроенный API пакета async-mutex.
- `Atomics` — с байтовыми массивами. `for await` и async-генераторы — с итераторами.

## План реализации

На каждом шаге: тесты `tests/run` с `// same-as-node` — порядок как в node, поэтому вывод
async-программ без зависимости от времени сравнивается с node напрямую; ошибки в
`tests/errors`; прогон под `TZ_CHECK_LEAKS=1`; обновление README.

1. **Async в одном потоке — ровно как node** (сделано). Async-функции как конечные автоматы, `Promise`
   (встроенный, как `Array`), очередь микрозадач, цикл событий, таймеры, `await` на верхнем
   уровне, не пойманная ошибка в задаче, ошибка на забытый `Promise`, `void`. После исключений
