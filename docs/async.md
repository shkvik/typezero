# Async

Решения, принятые 21 и 23 октября 2026 года, и поправки 26 октября: `Promise` не отклоняется,
асинхронная ошибка — `Promise<Result<T, E>>` ([errors.md](errors.md), раздел 4). Шаги 1–4 плана
сделаны 24–25 октября, шаг 7 — 27 октября; что осталось — в конце, в разделе «План реализации».

## Коротко

- `async` / `await` по умолчанию выполняются параллельно на всех ядрах, без пометок. Память
  общая. `go`, каналов и ручных потоков нет.
- Результат программы — такой, какой мог бы выдать node. Программа без ввода-вывода печатает
  одно и то же на каждом запуске, ровно как node.
- Куски кода, которые трогают одни и те же изменяемые данные, идут по очереди в порядке node,
  остальные — параллельно. Компилятор показывает, что и почему идёт по очереди.
- `Promise`, которого никто не ждёт, — ошибка компиляции; «запустить и не ждать» — `void f()`.
  Задача, которую не ждут, разбирает свои ошибки сама.
- `Promise` и таймеры — как в node, но `Promise` никогда не отклоняется: ошибка лежит в
  `Result` внутри.
- Общие объекты (`shared`) и `Mutex` отложены.

## 1. Как это устроено в node

```ts
async function load() {
  const text = await readFile("a.txt", "utf8")   // load «засыпает» здесь
  console.log(text.length)                       // продолжение — когда текущий код закончится
}
```

JS выполняется в одном потоке. Ждёт не JS: файл читает ОС, ответ сети ждёт ОС. Очередей две:
- **события** — «файл прочитан», «пришёл ответ», «сработал таймер»;
- **микрозадачи** — продолжения после `await` и колбэки `.then`.

Цикл node: выполнить основной код целиком; дальше, пока есть чего ждать, — все микрозадачи, одно
событие, снова все микрозадачи и т.д. Работающий код никогда не прерывают, поэтому **между двумя
`await` никто не вмешивается**. Код на JS на это рассчитывает, и tz это сохраняет.

## 2. Что идёт параллельно

**Кусок** — код между двумя `await` (или от начала функции до первого `await`). Куски разных
задач идут одновременно, если не трогают одни и те же изменяемые данные: одна задача данные
меняет, а другая меняет или читает. Данные, которые все только читают, делятся свободно. Вывод
на экран — тоже общие данные: его «меняет» каждый, кто печатает.

Параллельно может пойти только то, чего программа не ждёт сама: `Promise.all`, несколько запросов
к серверу, `void f()`. Обычный код (циклы, `map` без `async`) компилятор сам не распараллеливает.

```ts
async function convert(file: string) {
  const text = await readFile(file, "utf8")
  const result = heavy(text)                // секунда расчёта, только свои данные
  await writeFile(file + ".out", result)
}
await Promise.all(files.map(f => convert(f)))
```

В node чтение и запись идут одновременно, а `heavy` — по одному: 4 файла ≈ 4 с. В tz четыре
`heavy` идут на четырёх ядрах ≈ 1 с.

| Что в куске | Как идёт |
|---|---|
| только свои данные (пример выше) | параллельно |
| расчёт, потом `done++` или `results.push(r)` | расчёт параллельно, по очереди только `done++` |
| прочитал общее → долго считаешь → записал общее (`cache.get` … `heavy` … `cache.set`) | по очереди: в JS между `get` и `set` никто не вмешается, и код на это рассчитывает |
| `console.log` → долго считаешь → `console.log` | по очереди: node никогда не напечатает «начал a», «начал b» подряд |
| расчёт сам пишет в общую таблицу | по очереди |
| `for (const f of files) await convert(f)` | по очереди по смыслу: программа сама ждёт каждый |

- **По очереди идёт только участок** от первого до последнего обращения к общим данным внутри
  куска, а не весь кусок и не вся функция.
- **Как ускорить «прочитал → считаешь → записал»** — так же, как в JS: поставить `await` между
  чтением и записью. Это явное «здесь другие могут вмешаться».
- **Вывод tz не копит.** `console.log` вокруг тяжёлой работы делает её последовательной; нужен
  параллельный расчёт — собрать строки и напечатать после.
- **Порядок ввода-вывода, написанный программистом, tz не меняет:** его видно снаружи (другая
  программа может смотреть на каталог).
- **Компилятор не уверен** (не знает, что трогает функция) — по очереди. Программа компилируется
  целиком, поэтому обычно он видит все вызовы.

## 3. Порядок

Гарантия: **результат — такой, какой мог бы выдать node**.

```ts
async function work(n: int) {
  const r = await heavy(n)       // расчёт без ввода-вывода
  console.log("готово", n)
  return r
}
await Promise.all([work(1), work(2), work(3)])
```

- **Где у node порядок жёсткий** (расчёты без ввода-вывода, как здесь), куски с общими данными
  идут в порядке node: всегда «готово 1», «готово 2», «готово 3», даже если `heavy(2)` кончился
  раньше. Сами `heavy` идут параллельно, ждут только короткие участки с общими данными.
- **Где порядок в node зависит от времени** — файлы, сеть, таймеры, запросы к серверу, — tz
  выбирает любой порядок, который мог случиться и в node. Здесь параллельность ничем не
  ограничена, кроме общих данных.
- Ошибку в программе без ввода-вывода, которая случилась один раз, можно повторить: результат
  на каждом запуске одинаковый.

## 4. Точность анализа

Сначала компилятор различает:
- разные поля одного объекта (`stats.read++` и `stats.converted++`);
- объекты, которые каждая задача создаёт сама;
- свою ячейку массива: `results[i] = ...` внутри `map((f, i) => ...)`, если длина массива не
  меняется.

Чего при компиляции не видно — один объект дважды в общем массиве (`[a, a]`), ключи `Map`,
известные только при выполнении, — то идёт по очереди. Позже это можно проверять при выполнении:
замок на каждом общем объекте или ключе `Map` (разные — параллельно, одинаковые — по очереди).
Цена — атомарная операция при обращении и только у объектов, которые параллельные задачи делят
на деле; для `Map` — многопоточная реализация.

Точность анализа меняет только скорость, не результат: программы от уточнений не меняются,
только ускоряются.

## 5. Подсказки

Это подсказки, а не ошибки: код корректен, просто медленнее, чем мог бы быть.

- В редакторе: подчёркнут участок, из-за которого куски идут по очереди («по очереди с
  другими `convert`: все пишут в `cache`», переход ко второму месту по клику); у `Promise.all`
  — пометка «параллельно» или «по очереди (`cache`)»; над функцией — с чем она идёт
  параллельно.
- `tz build --explain-parallel` — то же текстом; вывод в JSON для инструментов. Анализ сразу
  выдаёт решения в структурированном виде, редактор потом просто читает готовое.
- Профиль при выполнении: сколько задачи реально ждали друг друга — чтобы подсвечивать то, что
  действительно тормозит.

## 6. `Promise`, которого никто не ждёт

```ts
save("Ann")              // ошибка, подсказка: await save("Ann") или void save("Ann")
void save("Ann")         // ок — явно «запустить и не ждать»
const p = save("Ann")    // ок, дождёмся позже
await p

names.forEach(async n => { await save(n) })
// ошибка: forEach выбрасывает Promise из колбэка, функция закончится раньше, чем всё сохранится;
// подсказка: for (const n of names) await save(n) или await Promise.all(names.map(n => save(n)))
```

Так же, как забытый `Result` ([errors.md](errors.md)). В node такой `Promise` выполняется сам по
себе, а если бросит — программа падает.

`void` над `Promise<Result<...>>` — тоже ошибка: `Err` пропал бы молча. Задача, которую не ждут,
разбирает ошибку сама, и колбэк с `Result` нельзя передать туда, где ждут `() => void`
(слушатель, таймер, `forEach`) — [errors.md](errors.md), раздел 4:

```ts
void save("Ann")                     // ошибка, если save возвращает Promise<Result<...>>

async function saveOrLog(name: string) {
  const r = await save(name)
  if (r.isErr()) console.error(r.error)
}
void saveOrLog("Ann")                // ок: Promise<void>
```

## 7. Как в node

- Async-функция при вызове выполняется сразу, до первого `await`.
- `Promise`: `new Promise((resolve) => ...)`, `then`, `Promise.all` / `race` / `resolve` /
  `withResolvers`. Объекты со своим методом `then` `await` не разворачивает — только настоящий
  `Promise`: tz не вызывает код программиста неявно.
- **`Promise` не отклоняется** ([errors.md](errors.md), раздел 4). Операция, которая может не
  получиться, отдаёт `Promise<Result<T, E>>`; методов `Result` у `Promise` нет — сначала `await`.
  Уходят `reject` (у `new Promise` и `withResolvers`), `.catch`, `.finally`, `Promise.reject`,
  `allSettled`, `any`. Несколько сразу: `Promise.all` отдаёт каждый `Result` отдельно,
  `Result.combine(await Promise.all(ps))` — все значения или первая ошибка.
- Лишний `return await x` в `async`-функции — ошибка: `async`-функция и так дождётся `Promise`.
- Таймеры: `setTimeout`, `setInterval`, `clearTimeout`, `clearInterval`, `setImmediate`;
  `await setTimeout(100)` из `"node:timers/promises"` — пауза.
- `await` на верхнем уровне модуля — как в ES-модулях. Программа завершается, когда не осталось
  задач, таймеров и ожидающего ввода-вывода.
- Не пойманных ошибок в задачах нет: `Result` нельзя выбросить (раздел 6).
- Отмена — `AbortController` / `AbortSignal`: сигнал передают явно (`timers/promises`,
  `fs/promises`, сеть). Операция с сигналом отдаёт `Err` с `{ code: "ABORT_ERR" }`; задача
  проверяет `signal.aborted`, `signal.throwIfAborted()` нет — вместо него
  `if (signal.aborted) return err(signal.reason)`. `Promise.race` не отменяет проигравших.
- `node:worker_threads` нет: параллельность и так есть.

## 8. Рантайм

- Пул рабочих потоков — по одному на ядро. `TZ_THREADS=N` задаёт число потоков вместе с главным.
- **Как куски идут параллельно.** Порядок node держит главный поток: цикл событий, очередь
  микрозадач, таймеры. Кусок после `await`, который может идти одновременно с другими, рантайм
  отдаёт свободному потоку, как только тот встал в очередь за тем, что главный поток выполняет.
  Поток выполняет кусок заранее, пока тот трогает только свои данные и то, что никто не меняет, и
  перед первым обращением к общим данным ждёт своей очереди. Когда главный поток доходит до куска,
  он отдаёт ему очередь и ждёт, пока кусок закончится в своём потоке. Так результат — порядок node,
  а расчёты до первого общего обращения идут на всех ядрах.
- Кусок, который один ждёт чтения файла (`node:fs/promises`), уходит в поток, как только файл
  прочитан, а событие чтения цикл проводит, когда кусок дойдёт до общих данных: время событий
  ввода-вывода в node тоже решает система.
- **Сервер** ([net.md](net.md)). События соединений `serve` приходят не в главный поток, а в
  потоки пула (у них свой порт IOCP). Поток, который прочитал заголовок запроса, сам выполняет
  кусок, ждавший его: `Request`, обработчик, ответ, ожидание следующего запроса. Пока кусок не
  трогает общих данных, главный поток о нём не знает; тронул — ждёт очереди, и событие проводится
  тогда, как выше. Функции рантайма для соединения очереди не ждут: соединение трогает только его
  задача, под замком соединения. Микрозадачи такого куска (`await` готового значения, `Promise`,
  который видит только он) выполняются в том же потоке после него. «Hello, World!» — 314 тыс.
  запросов в секунду против 239 тыс. у Go. Обработчик, который трогает общие данные, идёт в
  порядке node через главный поток (92 тыс.). Async-обработчик с `await` пока тоже: его аргументы
  становятся общими (его куски могут идти в других потоках), а с ними и его `Promise`, который без
  очереди менять нельзя (85 тыс.).
- Отдать кусок потоку стоит микросекунды, поэтому каждый `await` учится, сколько его куски идут до
  первого общего обращения, и короткие (до 30 мкс) выполняет в главном потоке.
- Программа без таких кусков собирается с рантаймом одного потока и ничего за потоки не платит.
- Ожидание ввода-вывода — IOCP в Windows, epoll / io_uring в Linux. Пока задача ждёт, её поток
  выполняет другие.
- **Вытеснение: долгий кусок не задерживает остальных.** Кусок между `await` занимает поток до
  конца — сохранить его посреди работы негде, своего стека у задачи нет. Поэтому за потоками
  следит рантайм. Если все потоки пула дольше ~10 мс заняты каждый одним куском (долгий расчёт или
  синхронный ввод-вывод вроде `readFileSync`), а другие куски ждут, рантайм берёт запасной поток
  (не больше, чем потоков в пуле), и ОС делит ядра между ними.
  - Так быстрые запросы не ждут тяжёлых. В Go для этого долгую горутину прерывают примерно
    через 10 мс.
  - Запасной поток дешёвый: создать — 40 мкс, разбудить — 2 мкс, ~17 КБ памяти (мерили для
    фонового освобождения). Число запасных потоков ограничено.
  - Правило D и порядок node не страдают: долгий кусок для программы по-прежнему выполняется
    целиком, а задачи, которым нужны его данные, ждут, как и раньше.
- Async-функции превращаются в конечные автоматы средствами LLVM (те же проходы, что у корутин
  C++20).
- Счётчики ссылок обычные (не атомарные), пока объект виден одному потоку. Общим (с атомарным
  счётчиком) объект становится, когда его может достать другой поток: его кладут в глобальную
  переменную, которую видят функции, или в общий объект, передают async-функции, чьи куски идут
  заранее, выполняют им `Promise`. Общим тогда становится и всё, что в нём лежит; компилятор
  ставит эти места в коде, а рантайм обходит объект по описанию его полей. Группу объектов в
  циклах ([objects.md](objects.md)), которую видит один поток, он и меняет без замка; общие
  группы меняются под одним замком.
- У каждого потока своя куча; блок, освобождённый чужим потоком, уходит в атомарный список кучи
  владельца, и тот забирает его, когда ему не хватит места.
- Освобождение больших групп объектов в фоне отложено ([objects.md](objects.md), шаг 10): пока
  группа освобождается сразу, в потоке, где умерла.

## 9. Отложено

- **Общие объекты** — чтобы сотни обработчиков запросов, которые трогают один `cache`, шли
  параллельно: каждый вызов метода берёт замок объекта только на время вызова. Обсуждали
  декоратор `@shared class Cache` (синтаксис TS) и правила: поля закрыты, в методах нет `await`,
  наружу — только неизменяемые значения или другие общие объекты.
- **`Mutex` / `Semaphore`** — атомарность через `await`. Пока — как в JS: между `await` другие
  задачи могут вмешаться. Обсуждали встроенный API пакета async-mutex.
- `Atomics` — с байтовыми массивами. `for await` и async-генераторы — с итераторами.

## План реализации

На каждом шаге: тесты `tests/run` с `// same-as-node` — порядок как в node, поэтому вывод
async-программ без зависимости от времени сравнивается с node напрямую; ошибки в
`tests/errors`; прогон под `TZ_CHECK_LEAKS=1`; обновление README.

1. **Async в одном потоке — ровно как node** (сделано). Async-функции как конечные автоматы, `Promise`
   (встроенный, как `Array`), очередь микрозадач, цикл событий, таймеры, `await` на верхнем
   уровне, не пойманная ошибка в задаче, ошибка на забытый `Promise`, `void`. После исключений
   ([errors.md](errors.md), шаг 2): на них держится `reject`.
2. **Ожидание ввода-вывода** (сделано): IOCP / epoll, `node:fs/promises`, `node:timers/promises`,
   `node:readline`, `AbortController` ([io.md](io.md), шаг 4).
3. **Анализ данных кусков** (сделано): что каждый кусок читает и пишет (поля, объекты, глобальные
   переменные, вывод), решения «параллельно / по очереди» в структурированном виде,
   `--explain-parallel`. Выполнение пока в одном потоке — проверяется по выводу пояснений.
4. **Параллельный рантайм** (сделано, кроме фонового освобождения): пул потоков, куча на каждый
   поток (списки освобождения между потоками в аллокаторе), атомарные счётчики у объектов, которые
   переходят между задачами, параллельное выполнение независимых кусков, порядок node для кусков
   с общими данными, вытеснение (запасные потоки, когда кусок держит поток дольше ~10 мс),
   `TZ_THREADS`, запросы `serve` в потоках пула. Код встроенных модулей на tz анализ не обходит:
   куски цикла соединений `serve` помечены в нём самом, а внутренности `fetch` и потоков идут в
   главном потоке. Фоновое освобождение больших групп ([objects.md](objects.md), шаг 10)
   отложено.
5. **Подсказки в редакторе** — вместе с языковым сервером; профиль ожиданий при выполнении.
6. **Позже:** проверки при выполнении (замки на объектах и ключах `Map`), общие объекты и
   `Mutex` — после решений по ним.
7. **Без отказов** (сделано 27 октября; [errors.md](errors.md), шаг 3): убрать `reject`, `.catch`, `.finally`,
