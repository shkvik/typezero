# Перегрузка

Решения, принятые 24 октября 2026 года. Шаг 1 плана (запрет у обычных функций) сделан 24 октября;
остальное — в конце, в разделе «План реализации».

## Коротко

- Перегрузка — как в C#: несколько тел с одним именем, вариант выбирает компилятор по типам
  аргументов, при компиляции. Отдельный вариант — отдельное тело.
- Можно у методов (и `static`) и у конструкторов. У обычных функций — нельзя: разные функции —
  разные имена.
- Вид из TS — несколько сигнатур над одним телом, которое само разбирает, что пришло, — ошибка.
- tsc такого не понимает, а node выполняет неправильно: такой код работает только в tz.

## 1. Как пишут

```ts
class Vec {
  constructor(public x: double, public y: double) {}
  constructor(p: Vec) { this.x = p.x; this.y = p.y }

  add(v: Vec) { return new Vec(this.x + v.x, this.y + v.y) }
  add(k: double) { return new Vec(this.x + k, this.y + k) }

  static of(x: double) { return new Vec(x, x) }
  static of(x: double, y: double) { return new Vec(x, y) }
}

v.add(w)            // add(v: Vec)
v.add(2)            // add(k: double)
new Vec(1, 2)       // constructor(x, y)
new Vec(v)          // constructor(p: Vec)
```

Каждый вариант — отдельная функция в exe, вызов — прямой, проверки типа при работе нет. Тип
результата у каждого варианта выводится свой.

**Обычные функции** не перегружаются: два `function area` в одной области — ошибка
«повторное объявление» с подсказкой дать разные имена (`circleArea`, `rectArea`).

## 2. Выбор варианта

- **Подходят** варианты с таким же числом аргументов (с учётом необязательных параметров,
  значений по умолчанию и `...rest`), у которых каждый аргумент передаётся без явного перевода:
  тот же тип, `int` → `long` → `double`, класс → его родитель, `T` → `T | undefined`.
- **Лучший** — тот, у которого каждый аргумент подходит не хуже, а хотя бы один — лучше: точное
  совпадение лучше расширения, `int` → `long` лучше, чем `int` → `double`. При прочих равных
  вариант без generics лучше обобщённого, а вариант без значений по умолчанию и `...rest` лучше,
  чем с ними. Как в C#.
  ```ts
  scale(k: int) { … }
  scale(k: double) { … }

  v.scale(2)      // int: литерал 2 — int
  v.scale(2.5)    // double
  v.scale(n)      // по типу n
  ```
- **Ни одного** подходящего или **два одинаково хороших** — ошибка компиляции со списком
  вариантов и тем, почему каждый не подошёл.

## 3. Ошибки в объявлениях

- Варианты, которые различаются только типом результата, — ошибка.
- Варианты, которые подходят к одному и тому же вызову одинаково (`f(x?: int)` и `f()`,
  `f(a: int, b = 0)` и `f(a: int)`), — ошибка уже в объявлении.
- Вид из TS — сигнатуры без тела над одним телом — ошибка и у методов, и у функций:
  ```ts
  add(v: Vec): Vec
  add(k: double): Vec
  add(a: Vec | double): Vec { … }   // ошибка: у каждого варианта — своё тело
  ```
  Сигнатуры без тела остаются там, где тел нет вообще: в `interface`, в типах, в `declare` —
  они описывают варианты, которые реализует класс, или чужой код.

## 4. Наследование и интерфейсы

- Наследник может добавить свои варианты; варианты родителя тоже участвуют в выборе, как в C#.
- `override add(k: double)` переопределяет ровно этот вариант; сигнатура должна совпасть.
- Вызов через тип родителя: вариант выбирается по типу переменной при компиляции, тело — по
  настоящему классу объекта при работе, как у любого метода.
- Конструкторы наследника вызывают нужный вариант родителя через `super(…)` по тем же правилам.
- Интерфейс с несколькими сигнатурами `add` — класс должен реализовать каждую своим телом.

## 5. Метод как значение

```ts
const f = v.add                              // ошибка: какой из add? — add(v: Vec) или add(k: double)
const g: (k: double) => Vec = v.add          // ок: тип подсказывает
[1, 2].map(v.add)                            // ок: колбэк получает double
```

Так же с `bind`, `call`, `apply`. Класс как значение (`Constructor`, [decorators.md](decorators.md))
с несколькими конструкторами: `new cls(…)` выбирает вариант так же — по типам аргументов.

## 6. Декораторы и отражение

- Декоратор на варианте получает этот вариант; `design:paramtypes` — его параметры
  ([decorators.md](decorators.md)).
- Метаданные пишутся по имени метода, как у метода без перегрузки. Если два варианта пишут по
  одному ключу — ошибка компиляции (как у `static` и обычного члена с одним именем).
- `Reflect.get(obj, "add")` и `Reflect.construct(cls, args)` — выбирают вариант по типам
  аргументов при работе; не подошёл ни один или подошли два — `TypeError`.

## 7. node и tsc

- node выполняет такой код неправильно: второе тело затирает первое (проверено на функциях:
  `area(2)` при `area(r)` и `area(w, h)` — `NaN`). Поэтому код и пакеты с перегрузкой работают
  только в tz, а тесты с ней не сравниваются с node.
- tsc пишет «Duplicate function implementation» (TS2393), про конструкторы — «Multiple
  constructor implementations are not allowed» (TS2392): подчёркивание в редакторе до своего
  языкового сервера. На мнение tsc не равняемся.
