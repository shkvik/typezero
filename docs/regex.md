# Регулярные выражения

Решения, принятые 23 октября 2026 года. Пока ничего из этого не реализовано: порядок работ — в
конце, в разделе «План реализации».

## Коротко

- Синтаксис и поведение — как в JS: все флаги, группы, `(?=…)` и `(?<=…)`, `\p{L}`.
- Регулярка из кода компилируется в машинный код при сборке. Цель — не медленнее node и
  Rust, в 7–40 раз быстрее Go, и без взрыва перебора, которым страдает node.
- Типы берутся из самой регулярки: группы, флаг `g`.
- Ловушки JS — ошибки компиляции: `test()` с `g`, `replace` со строкой, `replaceAll` без `g`,
  `match` со строкой, ссылка на группу, которой нет.
- Нет совпадения — `undefined`: `null` в tz бывает только в `Json` ([modules.md](modules.md)).

## 1. Движок и скорость

20 МБ текста, лучшее из трёх запусков:

| | node 24 | Rust (крейт regex) | Go 1.23 |
|---|---|---|---|
| `[a-z]+ing` — посчитать | 47 мс | 24 мс | 418 мс |
| даты — `replace("$3.$2.$1")` | 19 мс | 24 мс | 347 мс |
| `agggtaaa\|tttaccct` без регистра | 6 мс | 13 мс | 496 мс |
| `\b(?:error\|warning\|fatal)\b` | 11 мс | 16 мс | 347 мс |
| `(\w+)ing (\w+)` — `matchAll` с группами | 66 мс | 138 мс | 571 мс |
| `/^(a+)+$/` на `"aaa…ab"` | 30 букв — 25 с | 1 млн — 1 мс | 1 млн — 21 мс |

- **node** перебирает варианты в машинном коде, который V8 строит при запуске. С группами —
  быстрее всех, но на плохой регулярке время растёт взрывом: 28 букв — 0,75 с, 30 — 25 с.
- **Rust** ищет автоматом в машинном коде: один проход по строке, взрыва не бывает; группы
  достаёт медленнее перебора.
- **Go** тоже ищет автоматом, но без машинного кода — поэтому медленнее в 4–80 раз.

**В tz** регулярка из кода (`/…/`) компилируется в машинный код при сборке, и способ компилятор
выбирает для каждой:

- где совпадение — автомат, как в Rust;
- группы — перебор, как в V8, если компилятор доказал, что у этой регулярки перебор не
  взорвётся; иначе автомат;
- с обратной ссылкой (`\1`) — только перебор, как в JS: автомату она не по силам.

Ожидание — в каждом тесте не хуже лучшего из node и Rust, и без компиляции при запуске.

- **`new RegExp(строка)`** — регулярка известна только во время работы: её выполняет
  интерпретатор того же движка. В exe он попадает, только если в программе есть `new RegExp`.
- **Движок свой, с правилами JS**, а не PCRE: результаты совпадают с node. Пример разницы:
  `/(?:(a)|b)+/.exec("ab")` в JS — `[ 'ab', undefined ]` (группы в повторе сбрасываются), в
  PCRE — `[ 'ab', 'a' ]`.
- Строки в tz хранятся как в V8 — по байту или по два на символ ([README](../README.md)),
  поэтому код каждой регулярки — в двух вариантах.

## 2. Типы

```ts
const m = date.match(/(?<year>\d{4})-(?<month>\d{2})(-\d{2})?/)
if (m) {
  m.groups.year          // string (tsc: ошибка — groups может быть undefined)
  m[3]                   // string | undefined — группа с ?
  m[4]                   // ошибка: групп три
  m.index                // int
}

"a1b22".match(/\d+/)     // RegExpMatchArray | undefined
"a1b22".match(/\d+/g)    // string[] | undefined (tsc для обоих: RegExpMatchArray | null)

date.replace(/(\d+)-(\d+)/, (all, y, mon) => mon + y)   // y, mon: string
for (const { groups } of text.matchAll(/(?<key>\w+)=(?<value>\w+)/g))
  console.log(groups.key, groups.value)                  // string, string
```

- Группы, их имена и необязательность компилятор знает по регулярке; лишняя `m[4]` и `"$4"` в
  строке замены — ошибка (в JS `"$4"` молча вставляется как текст).
- У `new RegExp(s)` групп не знает никто: `m[1]` и `groups.x` — `string | undefined`.
- Регулярка, пришедшая параметром `re: RegExp`, — флаг `g` неизвестен, поэтому `match` — ошибка
  с подсказкой: `exec` (одно совпадение) или `matchAll` (все).
- Нет совпадения — `undefined`; `if (m)`, `m?.[1]`, `m ?? []` работают как в JS
  ([small.md](small.md), раздел 1).

## 3. Ошибки компиляции вместо ловушек

| Код | node | tz |
|---|---|---|
| `re.test(s)`, где у `re` флаг `g` | ответ зависит от прошлого вызова (раздел 4) | ошибка → убери `g` |
| `"a-b-c".replace("-", "+")` | `"a+b-c"` — только первое | ошибка → `replaceAll("-", "+")` или `replace(/-/, "+")` |
| `"aaa".replaceAll(/a/, "b")` | `TypeError` при работе | ошибка → `/a/g` |
| `"aaa".matchAll(/a/)` | `TypeError` при работе | ошибка → `/a/g` |
| `"a1b".match(".")` | `[ 'a' ]`: строка стала регуляркой, `.` — любой символ | ошибка → `includes(".")` или `/\./` |
| `"цена 1.5".search(".")` | `0` | ошибка → `indexOf(".")` |
| `s.replace(re, "$4")` при трёх группах | вставит `"$4"` как текст | ошибка: группы 4 нет |
| `/[😀]/` без `u` | две половинки эмодзи по отдельности | ошибка → `/[😀]/u` |
| `/(/` | `SyntaxError` при разборе | ошибка компиляции |
| `RegExp.$1`, `re.compile()` | устаревшее, работает | ошибка |

## 4. Регулярка с `g` помнит, где остановилась

```ts
const word = /a/g
word.test("a")   // в JS: true, потом false, потом true — g запомнил место (lastIndex)
```

- **`test()` с `g` — ошибка** с подсказкой «убери `g`»: для вопроса «есть ли совпадение» флаг
  «найти все» ничего не даёт, кроме этой ловушки.
- **`exec()` с `g` или `y` — как в JS**: это цикл по совпадениям, `lastIndex` двигается.
  ```ts
  let m
  while ((m = re.exec(text)) != undefined) console.log(m.index)
  for (const m of text.matchAll(re)) console.log(m.index)      // то же, проще
  ```
- **`test()` с `y` — как в JS**: так разбирают текст с нужной позиции (`re.lastIndex = pos`).
- Регулярка без `g` и `y` состояния не хранит, и параллельные async ([async.md](async.md))
  делят её без очереди. С `g` и `y` — состояние: доступ к ней идёт по очереди, как к любым
  общим данным.

## 5. `replace` со строкой — ошибка

В JS `"a-b-c".replace("-", "+")` даёт `"a+b-c"`: заменяется только первое, хотя почти всегда
ждут все. В tz это ошибка, и надо написать явно:

- все — `replaceAll("-", "+")`;
- только первое — регуляркой: `replace(/-/, "+")`. Подсказка сама экранирует особые символы:
  для `"."` — `/\./`, для строки из переменной — `new RegExp(RegExp.escape(sep))`.

`replace` с регуляркой — как в JS.

## 6. Как в JS

- Весь синтаксис и флаги: `g i m s u v y d`, `(?=…)`, `(?!…)`, `(?<=…)`, `(?<!…)`, именованные
  группы, `\p{L}` с `u` и `v`, `\1` и `\k<name>`.
- `"a1b2".split(/(\d)/)` → `[ 'a', '1', 'b', '2', '' ]`: группы попадают в результат.
- `\d`, `\w`, `\b` — только латиница и цифры ASCII, даже с `u`.
- Без `u` — единицы UTF-16: `/^.$/.test("😀")` — `false`, с `u` — `true`.
- `RegExp.escape(s)` — для `new RegExp` из ввода.

## План реализации

На каждом шаге: тесты `tests/run` с `// same-as-node` (кроме печати несовпадения: node
печатает `null`, tz — `undefined`), ошибки в `tests/errors`, обновление README.

1. **Разбор при компиляции.** Синтаксис регулярок JS со всеми флагами; ошибки из раздела 3;
   типы групп и результатов (раздел 2). Нужны объекты для `RegExpMatchArray` с `index` и
   `groups` ([objects.md](objects.md), шаг 1).
2. **Интерпретатор** — перебор по правилам JS, для всех регулярок сразу: `test`, `exec`,
   `match`, `matchAll`, `replace` / `replaceAll` с регуляркой и функцией, `split`, `search`,
   `lastIndex`, `new RegExp`, `RegExp.escape`. Здесь результаты сверяются с node. `matchAll` —
   с итераторами ([iterators.md](iterators.md), шаг 1); `SyntaxError` из `new RegExp` — с
   исключениями ([errors.md](errors.md), шаг 2); группы `new RegExp` — со словарями
   ([objects.md](objects.md), шаг 7).
3. **Unicode** — флаги `u` и `v`, `\p{…}`, `/i` по таблицам Unicode.
4. **Компиляция в машинный код** — автомат для поиска совпадения с быстрым поиском первых
   букв, перебор для групп там, где компилятор доказал, что он не взорвётся, автомат там, где
   не доказал. Замеры в `bench` рядом с node, Rust и Go.
