# Декораторы

Решения, принятые 23 октября 2026 года. Пока ничего из этого не реализовано: порядок работ — в
конце, в разделе «План реализации».

## Коротко

- Декораторы — в синтаксисе старых декораторов TS (`experimentalDecorators`): классы, методы,
  поля, параметры. Стандартных декораторов TC39 в tz нет. Флагов нет.
- `any` нет. Декораторы пишутся с типами; где нужно «что угодно» — `unknown`.
- Декоратор всегда получает сам класс, где бы он ни стоял. Прототипов в tz нет.
- Метаданные — `Reflect.defineMetadata` / `getMetadata` встроены. Ключ — обычно сам декоратор,
  тип значения tz выводит сам.
- Декоратор может подменить класс; новые члены, которые он добавил, видны в типе класса.
- Отражение (reflection) — для библиотек: создать объект класса-значения, вызвать метод по
  имени, узнать поля класса. С проверками во время работы.
- Фреймворков в языке нет. DI, маршруты, ORM — библиотеки на tz поверх всего этого.
- На мнение tsc в редакторе не равняемся: у tz будет свой языковой сервер.

## 1. Виды декораторов

```ts
@Table("users")                                      // класс
class User {
  @Column name: string                               // поле
  @Column age: number = 0

  constructor(@Inject("DEFAULT_NAME") name: string) { // параметр конструктора
    this.name = name
  }

  @Log                                               // метод: обернуть
  add(a: number, b: number) { return a + b }

  @Deprecated("используй add")                       // метод: запомнить
  plus(a: number, b: number) { return a + b }
}
```

| Где стоит | Что получает декоратор |
|---|---|
| класс | `(класс)`; может вернуть другой класс (раздел 5) |
| метод | `(класс, имя, описание метода)`; может подменить `описание.value` |
| поле | `(класс, имя)` |
| параметр конструктора или метода | `(класс, имя метода или undefined, номер параметра)` |

То же для `static`-членов. Декоратор с параметрами (`@Table("users")`) — функция, которая
возвращает декоратор.

- **Декоратор всегда получает сам класс** — и у класса, и у полей, и у методов, и у параметров.
  В TS декораторы полей и методов получают прототип; в tz прототипов нет: `User.prototype` —
  ошибка компиляции, `target.constructor` — ошибка с подсказкой «декоратор и так получил класс».
- **Геттеров и сеттеров нет** ([objects.md](objects.md)), значит, и декораторов для них.
  `accessor x = 1` — обычное поле; декоратор на нём — ошибка: запись в поле не должна вызывать
  код.
- **Когда выполняются** — как в TS: один раз, при объявлении класса. Выражения декораторов
  вычисляются сверху вниз, применяются снизу вверх: сначала члены, потом параметры
  конструктора, потом класс.
- **Каждое применение компилируется отдельно**, как шаблон: параметры типа (`A`, `R` ниже)
  известны точно, обёртка метода вызывается напрямую, без поиска по имени.
- **Декоратор не на своём месте** (`@Log` на поле) — ошибка компиляции на этой строке.

## 2. Декоратор метода

```ts
export function Log<A extends unknown[], R>(_cls: object, name: string, method: MethodDescriptor<A, R>) {
  const original = method.value
  method.value = function (this: unknown, ...args: A): R {
    const result = original.apply(this, args)
    console.log(`${name}(${args.join(", ")}) → ${String(result)}`)
    return result
  }
}
```

`MethodDescriptor<A, R>` — встроенный тип, короткая запись для
`TypedPropertyDescriptor<(...args: A) => R>`: `A` — параметры метода, `R` — результат. При
использовании их не пишут: `@Log` над `add(a: number, b: number)` сам даёт
`A = [number, number]`, `R = number`.

## 3. Метаданные

```ts
// table.ts — весь декоратор
export function Table(name: string) {
  return (cls: object) => Reflect.defineMetadata(Table, name, cls)
}

// где угодно
Reflect.getMetadata(Table, User)           // "users", тип string | undefined
Reflect.getMetadata(Deprecated, User, "plus")
```

- **API — как у пакета reflect-metadata**, но встроенный: импорт не нужен.
- **Ключ — объект**, обычно сам декоратор. Тип значения tz выводит из всех записей по этому
  ключу во всей программе: по ключу `Table` пишет одна строка, и пишет она `string`. Своя
  таблица (`WeakMap`) и функция для чтения не нужны. Столкнуться с ключом другой библиотеки
  нельзя: ключ — объект, а не строка.
- **Ключ — строка** (`Reflect.getMetadata("table", User)`) — разрешено ради старого кода, но
  значение — `unknown`, его надо проверить перед использованием. Строковые ключи общие на всю
  программу, поэтому выводить по ним тип нельзя: вторая библиотека с тем же ключом сломала бы
  первую.
- **Все записи — на самом классе.** Если один и тот же декоратор стоит на `static`-члене и на
  обычном члене с тем же именем, их записи совпали бы — это ошибка компиляции.
- **Типы из кода** — `design:type`, `design:paramtypes`, `design:returntype` — компилятор
  записывает всегда, без флага `emitDecoratorMetadata`, и тип у них точный: класс или список
  классов.

## 4. `unknown`

`unknown` — значение чего угодно, которое нельзя использовать без проверки (`typeof`,
`instanceof`, `Array.isArray` и т.п.), как в TS. `any` в tz нет. `unknown` нужен там, где тип
известен только во время работы: строковые ключи метаданных, отражение, таблицы со значениями
разных типов в библиотеках.

## 5. Подмена класса

```ts
const created: object[] = []

function Registered<T extends Constructor>(cls: T) {
  return class extends cls {
    constructor(...args: ConstructorArgs) {
      super(...args)          // ровно параметры исходного класса
      created.push(this)
    }
  }
}

let nextId = 1
function WithId<T extends Constructor>(cls: T) {
  return class extends cls {
    id = nextId++
  }
}

@WithId
class Order {
  constructor(public total: number) {}
}

new Order(100).id    // 1, тип number
```

- Декоратор класса может вернуть другой класс — обычно наследника исходного. Дальше имя класса
  означает его.
- **Тип класса — тот, что вернул декоратор**, поэтому добавленные члены (`id`) видны и
  проверяются. В TS декоратор тип не меняет, и tsc подчеркнёт `order.id`; когда у tz будет свой
  языковой сервер, редактор будет показывать мнение tz.
- `Constructor<T>` — «любой класс, объекты которого — `T`»; `ConstructorArgs` — параметры
  конструктора исходного класса. Оба встроенные.
- Компилятор строит конкретный класс под каждое применение, поэтому базовый класс должен быть
  известен при компиляции: у объектов tz раскладка полей фиксирована. Примесь
  `Identified(Entity)` — можно; класс, выбранный во время работы, — ошибка.

## 6. Отражение

Нужно библиотекам, которые пишутся один раз и не знают классов программы: маршрутизатору, DI,
ORM, разбору тела запроса.

```ts
type Route = { path: string; cls: Constructor; method: string }
const routes: Route[] = []

function Get(path: string) {
  return (cls: Constructor, method: string) => { routes.push({ path, cls, method }) }
}

function handle(path: string): unknown {
  const route = routes.find(r => r.path == path)
  if (route == undefined) return "404"
  const controller = new route.cls()                 // класс известен только во время работы
  const method = Reflect.get(controller, route.method)  // метод по имени из строки
  if (typeof method != "function") return "500"
  return Reflect.apply(method, controller, [])
}
```

В JS это ничего не стоит: объекты там — словари. В tz поля и методы раскладываются при
компиляции, имён во время работы нет. Поэтому компилятор кладёт в exe описание классов — как
создать объект, какие у класса методы и поля и каких они типов:

- `new cls(...)` для класса-значения — аргументы проверяются по конструктору;
- `Reflect.get(obj, имя)` → `unknown`, `Reflect.apply(f, obj, args)` и
  `Reflect.construct(cls, args)` — аргументы проверяются по параметрам;
- список полей класса с типами — чтобы превратить JSON (`Json`, [modules.md](modules.md)) в
  объект нужного класса с проверкой каждого поля;
- не тот аргумент, нет метода, поле не того типа — `TypeError` с понятным текстом.

Описание попадает в exe только для классов, до которых отражение реально доходит (в примере —
`UsersController`, он попал в `routes` через `@Get`). Остальные классы ничего не платят.

## 7. Фреймворков в языке нет

DI в стиле NestJS (`@Injectable`, `@Inject`, внедрение по типу параметра конструктора),
маршруты (`@Controller`, `@Get`, `@Body`), ORM (`@Entity`, `@Column`) — библиотеки, написанные на
tz с помощью разделов 1–6. В язык не встраиваются. Сам NestJS на tz не скомпилируется: он
держится на динамике JS и прототипах; переносится стиль, а не библиотека.

## 8. Редактор

На мнение tsc не равняемся. Пока своего языкового сервера нет, tsc в редакторе подчёркивает
то, что tz принимает: декораторы без флага `experimentalDecorators`, `cls: Constructor` у
декоратора метода (tsc считает, что тот получает прототип), члены, добавленные подменой класса.
Свой языковой сервер покажет мнение tz.

## План реализации

На каждом шаге: тесты `tests/run`, ошибки в `tests/errors`, обновление README. Сравнение с
node — только для того, что ведёт себя одинаково: в node поля и методы получают прототип, а
`getMetadata` возвращает `any`.

1. **Декораторы** — классов, методов, полей, параметров, `static`-членов: разбор, порядок
   вычисления и применения, класс как первый аргумент, описание метода и `MethodDescriptor`,
   каждое применение отдельно, ошибки (не на своём месте, `prototype`, `accessor`). Нужны
   классы ([objects.md](objects.md), шаг 3) и generics ([generics.md](generics.md), шаг 1).
2. **Метаданные и `unknown`** — `defineMetadata` / `getMetadata` с ключом-объектом и выводом
   типа, строковые ключи с `unknown`, `design:*` от компилятора, ошибка на совпадение записей
   `static` и обычного члена.
3. **Подмена класса** — классы как значения, class-выражения и примеси (их
   [objects.md](objects.md) откладывает сюда), `Constructor`, `ConstructorArgs`, тип класса из
   результата декоратора, базовый класс только известный при компиляции. Нужно наследование
   ([objects.md](objects.md), шаг 4).
4. **Отражение** — описания классов в exe только для тех, до кого оно доходит; `new cls()`,
   `Reflect.get` / `apply` / `construct` с проверками; поля класса и перевод `Json` в объект.
5. **Позже:** когда класс известен при компиляции (`container.get(UserService)`), компилятор
   разворачивает отражение в прямые `new` и вызовы.
