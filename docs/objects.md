# Объекты и классы

Решения, принятые 22–23 октября 2026 года, и поправки 26 октября: приватное — только
`private`, печать и `JSON.stringify` выводят все поля, у библиотеки нет геттеров (разделы 4 и 6).
Шаги 1–9 плана сделаны 24–25 октября, шаг 10 отложен 25 октября, шаг 11 — поправки 26 октября;
подробности — в конце, в разделе «План реализации».

## Коротко

- Объект — ссылка на блок в куче, поля лежат без упаковки, прототипов нет.
- Типы объектов точные: объект с лишними полями не подходит туда, где ждут меньше. Подтипы
  бывают только объявленные явно: `extends` и `implements`.
- Классы различаются по имени. Литерал никогда не становится экземпляром класса.
- Через тип, который разрешает больше записей (`Animal[]` для `Dog[]`, изменяемое поле для
  `readonly`), можно читать, но нельзя писать. Компилятор проверяет это по всей программе.
- «Поля нет» и «поле равно `undefined`» — одно и то же. `delete obj.f` и `"f" in obj` для
  необязательных полей — ошибки компиляции.
- tz не вызывает код программиста неявно. `toString` — обычный метод, геттеров и сеттеров нет
  нигде, и в библиотеке тоже.
- Приватное — только `private`, `#x` — ошибка. `console.log` и `JSON.stringify` выводят все
  поля, и приватные; что отдать наружу, решает явный метод.
- Метод, взятый как значение, сам привязан к своему объекту. Заменить метод у объекта нельзя.
- Объединения объектов и простых типов есть. `switch` по ним обязан разобрать все варианты.
- `null` нет.
- Словари — это `Record` и `Map` / `Set`; ключи всегда идут в порядке добавления.
- Сборщика циклов нет. Циклы освобождает компилятор, а там, где он не может, — группы с общим
  счётчиком. Большие группы освобождаются в фоне.

## 1. Устройство объекта

Объект — ссылка (8 байт) на блок в куче: `[счётчик ссылок | описание | поля]`. Так же сейчас
устроены окружения замыканий (`{rc, drop, поля}` в `codegen_closure.cpp`), только место `drop`
займёт указатель на описание.

- **Поля хранятся без упаковки:** `int` — 8 байт (`int` — 64 бита, [numbers.md](numbers.md);
  `int32` — 4), `double` — 8, `boolean` — 1, ссылки — 8.
  Порядок полей в памяти выбирает компилятор: так, чтобы не было дыр на выравнивание, и так,
  чтобы поля родителя шли первыми.
- **Литерал** `{ x: 1, y: 2 }` — экземпляр анонимного класса. Литералы и классы устроены
  одинаково, отдельного медленного «объекта-словаря» нет.
- **Описание** — одно на каждую раскладку или класс, константа в exe. В нём лежат:
  - смещения полей;
  - имена полей и порядок ключей (для печати и `Object.keys`; он отдельный от порядка в памяти);
  - таблица методов;
  - родитель и имя класса;
  - функция освобождения;
  - номер класса для `instanceof`.
- **Прототипов нет.** Методы лежат в описании, а не в объекте, как в JS они лежат в прототипе.
- **`==`** сравнивает ссылки. **`Obj | undefined`** — ссылка или ноль, без отдельного флага.
- **Чтение поля** — одна загрузка по постоянному смещению: подтипы только объявленные, а поля
  родителя идут первыми. Исключение — интерфейс с полями, который реализуют несвязанные между
  собой классы. Тогда компилятор старается поставить его поля на одинаковые смещения, а если не
  выходит — читает через таблицу смещений (одна лишняя загрузка).

## 2. Типы объектов и совместимость

### Точные типы

Объект подходит к типу, только если у него ровно те же поля тех же типов. Одинаковый состав
полей — один и тот же тип, как бы он ни был назван (`interface`, `type`, литерал).

```ts
interface Point { x: double; y: double }
function len(p: Point) { return Math.hypot(p.x, p.y) }

const p3 = { x: 1.0, y: 2.0, z: 3.0 }
len(p3)                    // tsc: ок. tz: ошибка — у { x, y, z } лишнее поле z

type P = { x: double; y: double }
const a: P = { x: 1.0, y: 2.0 }
len(a)                     // tz: ок — тот же состав полей
```

Зачем: поле всегда лежит по известному смещению, лишние поля не утекают незаметно (в TS
`toPublic(userWithPassword)` отправит пароль в JSON), и опечатка в литерале — всегда ошибка.

### Подтипы — только объявленные

```ts
interface Named { name: string }
interface User extends Named { id: int; email: string }
class Company implements Named { constructor(public name: string, public inn: string) {} }

function greet(n: Named) { console.log("hi " + n.name) }
greet(user)               // tz: ок — User объявлен как Named
greet(company)            // tz: ок — implements Named
```

`implements` обязателен: класс без него к интерфейсу не подходит, даже если у класса все нужные
члены есть (в TS подходит). Если функции нужна часть объекта чужого типа, есть два пути:
- обобщённая функция `<T extends { name: string }>(u: T)`, где ограничение означает «есть хотя
  бы эти поля», — это придёт вместе с generics, и каждая копия знает точную раскладку;
- передать само значение: `greet(user.name)`.

### Классы различаются по имени

```ts
class Point { constructor(public x: double, public y: double) {} }
class Size  { constructor(public x: double, public y: double) {} }

const p: Point = { x: 1, y: 2 }   // tsc: ок (а p instanceof Point — false). tz: ошибка
const q: Point = new Size(1, 2)   // tsc: ок. tz: ошибка — Size не объявлен как Point
```

Экземпляр класса создаётся только через `new` этого класса или его наследника.

### Типы полей

Типы полей совпадают точно: `{ x: int }` не подходит к `{ x: double }`. Объект при
присваивании не копируется, поэтому одно поле не может лежать одновременно как `int` и как
`double`. Чтобы целые литералы не мешали, тип поля литерала выводится из того, куда объект
попадает дальше:

```ts
const p = { x: 1, y: 2 }
len(p)                    // tz: ок — p идёт в Point, поэтому x и y — double
```

Ошибка остаётся, только если один и тот же объект идёт и в `{ x: int }`, и в `{ x: double }`.

### Запись через более широкий тип

Одно правило на три случая: значение можно передать или присвоить туда, где тип разрешает
больше записей, чем его собственный, если такой записи на самом деле нигде нет. Компилятор
проверяет это по всей программе: прямые записи, записи в функциях, которым значение передали
дальше, и сохранение значения куда-то ещё. Ошибка показывается у вызова или присваивания и
называет строку, где запись.

```ts
class Animal { constructor(public name: string) {} }
class Dog extends Animal { bark() {} }
class Cat extends Animal {}

function names(pets: Animal[]) { return pets.map(p => p.name).join(", ") }
function adopt(pets: Animal[]) { pets.push(new Cat("Tom")) }
const dogs: Dog[] = [new Dog("Rex")]
names(dogs)               // tz: ок — names только читает
adopt(dogs)               // tsc: ок. tz: ошибка — adopt кладёт Cat в массив Dog[]

interface Owner { pet: Animal }
interface DogOwner extends Owner { pet: Dog }
function giveCat(o: Owner) { o.pet = new Cat("Мурка") }
const ivan: DogOwner = { pet: new Dog("Рекс") }
giveCat(ivan)             // tsc: ок. tz: ошибка — giveCat пишет Cat в поле pet: Dog

interface Settings { readonly port: int }
function resetPort(s: { port: int }) { s.port = 0 }
function show(s: { port: int }) { console.log(s.port) }
const settings: Settings = { port: 8080 }
show(settings)            // tz: ок
resetPort(settings)       // tsc: ок. tz: ошибка — resetPort пишет в readonly-поле
```

В TS это сознательные дыры в типах. У нас такая запись означала бы чтение поля `Dog` из объекта
`Cat`, то есть порчу памяти, поэтому их нужно закрыть, а правило выше закрывает их, не ломая код,
который только читает.

## 3. Необязательные поля, `in`, `delete`

Под необязательное поле в объекте всегда есть место. «Поля нет» и «поле равно `undefined`» —
одно и то же.

```ts
interface Query { text: string; limit?: int }
const a: Query = { text: "кошки" }
const b: Query = { text: "собаки", limit: undefined }

a.limit ?? 20             // node и tz: 20 — код, который читает поле, разницы не видит
console.log(b)            // node: { text: 'собаки', limit: undefined }. tz: { text: 'собаки' }
"limit" in b              // tz: ошибка, подсказка: b.limit != undefined
delete b.limit            // tz: ошибка, подсказка: b.limit = undefined

const defaults = { limit: 20 }
const final = { ...defaults, ...b }
final.limit               // node: undefined — явный undefined затёр 20. tz: 20
```

Spread не копирует `undefined` из необязательных полей, поэтому классический баг JS, когда
явный `undefined` затирает значение по умолчанию, исчезает. `JSON.stringify` и в JS выбрасывает
`undefined`, так что там разницы нет.

`in` остаётся для объединений: `"radius" in shape` выбирает вариант `Circle` из `Circle | Square`
(см. раздел 7).

## 4. Ничего от `Object.prototype`

Объект не наследует ничего:
- `toString()` — обычный метод программиста. `"" + obj` и `` `${obj}` `` — ошибки компиляции,
  даже если в классе есть `toString`: пиши `` `${m.toString()}` ``. `"[object Object]"` не
  появляется никогда.
- `valueOf` и `hasOwnProperty` нет.
- `toString` у чисел, строк и массивов (`(255).toString(16)`, `[1, 2].toString()`) — их
  собственные встроенные методы, они остаются.

**Принцип: tz не вызывает код программиста неявно** — ни по имени метода (`toString`,
`valueOf`), ни при чтении поля (геттеры).
- **`toJSON`** `JSON.stringify` сам не вызывает. Что отдать наружу, решает явный вызов:
  `JSON.stringify(user.toJSON())`; если у класса есть `toJSON`, а его не вызвали, компилятор
  подсказывает эту запись. `replacer` тоже не поддерживается.
- **Пометок, которые читают встроенные функции, нет.** Декоратор программиста может записать
  метаданные (`Reflect.defineMetadata`), но `console.log` и `JSON.stringify` их не читают:
  встроенной пометки «не выводить это поле» нет.
- **`[Symbol.iterator]`** в `for...of` вызывается: по типу видно, чей метод сработает
  ([iterators.md](iterators.md)).

## 5. Методы и `this`

- `this` есть в методах классов и литералов, как в JS. Стрелка внутри метода видит его `this`.
  У `function` своего `this` нет (так уже сейчас): `this` внутри неё — ошибка с подсказкой
  написать стрелку.
- Метод, взятый как значение, привязан к своему объекту: `const inc = counter.inc; inc()` и
  `onClick(counter.inc)` работают (в JS — `TypeError`). `counter.inc == counter.inc` — `true`.
  `bind` для этого не нужен.
- Заменить метод у объекта нельзя: `s.save = () => ...` — ошибка (метод — часть класса, а не поле
  объекта). Если поведение должно подменяться, например в тестах, нужно объявить поле с
  функцией: `save: () => void = () => ...`.
- Стрелка в поле класса (`onClick = () => { this.clicks++ }`) работает. Если поле никто не
  переприсваивает, оно компилируется как метод: без отдельной функции в каждом объекте и без
  цикла ссылок «объект → функция → объект».
- **Метод интерфейса и поле с функцией взаимозаменяемы, как в TS.** Член интерфейса,
  объявленный методом (`query(sql: string): string[]`), — это поле с функцией, которое через
  этот интерфейс нельзя заменить, то есть `readonly`. Его реализует и метод, и стрелка в поле:
  `const handlers: Handlers = { onClick: x => ... }` работает. Член, объявленный полем
  (`query: (sql: string) => string[]`), можно заменить через интерфейс, но если в переменной на
  самом деле объект, где это метод, — ошибка по правилу записи через более широкий тип (раздел 2).
  При вызове через интерфейс, до которого доходят оба вида, поле вызывается через маленькую
  заглушку-метод (одна лишняя загрузка). Обобщённый метод интерфейса (`map<U>(...)`) реализуется
  только методом: стрелка в поле была бы обобщённой функцией-значением, а их нет (см.
  [generics.md](generics.md), раздел 6).

## 6. Классы

Как в TS: `constructor`, параметры-свойства (`constructor(public x: int)`), `extends` / `super`
(до `super()` `this` нельзя), `override`, `abstract`, `static` (глобальные переменные класса),
`private` / `protected` (проверяются при компиляции), `implements` (обязателен), `instanceof`.

- **Приватное — только `private`.** `#x` — ошибка с подсказкой `private x`: одна система
  модификаторов вместе с `protected` и `public`, и `private` работает в параметрах-свойствах
  (`constructor(private db: Db)`), где `#` нельзя. Совместимость с JS здесь не цель.
- **`protected` — как в TS** (поправка 28 октября): наследник пользуется защищённым членом у
  `this` и у объектов своего класса (и его наследников), но не у любого объекта базового класса:
  в `class E extends Event` вызов `other.markTrusted()` у чужого `Event` — ошибка. Доступ к
  закрытому варианту перегрузки проверяется у варианта, который выбран.
- **Печать — все поля, и приватные:** `Account { pin: 1234, token: 'secret-abc', name: 'Ann' }`.
  Печать нужна для отладки, а отладке нужно всё состояние; так печатают Rust (`{:?}`), Go
  (`%+v`), Swift. В node `#x` не печатается — у нас `#x` нет.
- **`JSON.stringify` — тоже все поля, и приватные.** Что уходит наружу (клиенту, в лог,
  другой программе), решает явный метод:
  ```ts
  class Client {
    private apiKey: string
    baseUrl: string
    constructor(baseUrl: string, apiKey: string) { this.baseUrl = baseUrl; this.apiKey = apiKey }
    toJSON() { return { baseUrl: this.baseUrl } }
  }
  JSON.stringify(c.toJSON())   // {"baseUrl":"https://api.example.com"}
  JSON.stringify(c)            // всё, и apiKey
  ```
  Встроенной пометки, которая прячет поле, нет (раздел 4). Внутренняя пометка библиотеки
  `@__tz_hidden`, которая прятала поля ради печати как в node, убирается.
- **Вызов метода** прямой и может встроиться, если метод никто не переопределяет. Компилятор
  видит всех наследников. Иначе метод вызывается через таблицу методов.
- **`instanceof`** — одно сравнение: номера классов раздаются так, что потомки занимают
  сплошной диапазон.
- **Инициализация.** Поле без `?` должно получить значение — при объявлении или в конструкторе.
  Пока заданы не все поля, `this` можно использовать только для записи полей: никаких вызовов
  методов и передачи `this` куда-то (как в Swift). `data!: string` («задам потом») — ошибка.
  ```ts
  class User {
    name: string
    email: string
    constructor(name: string) {
      this.name = name
      this.log()          // node: печатает "Ann <undefined>". tz: ошибка — email ещё не задан
      this.email = name.toLowerCase() + "@example.com"
    }
    log() { console.log(this.name + " <" + this.email + ">") }
  }
  ```
- **Конструктор не может не получиться** ([errors.md](errors.md), раздел 7): исключений нет, а
  `new` всегда даёт объект. Всё, что может не получиться, конструктор разбирает сам, или это
  проверяют до него типом аргумента. Если само создание может не получиться, конструктор
  закрыт (`private constructor`), а объект создаёт статическая функция с `Result`:
  `Port.parse(text)` — как в Rust и Go.
- **Родительский конструктор** не может вызывать метод, который переопределяет наследник: поля
  наследника в этот момент ещё не заданы (в node — `TypeError`). Это ошибка компиляции в
  родителе.
- **Геттеров и сеттеров нет** (`get area()`, `set width(v)`): чтение поля, которое на деле
  выполняет код, — скрытый вызов. Нужно писать методы `area()` и `setWidth(v)`. Отсюда же:
  чтение поля — всегда просто загрузка из памяти. Это касается и библиотеки (решено 27
  октября), правило одно — «поле можно читать всегда; меняет его только сам объект своими
  методами»:
  - значение, которое не меняется, — `readonly`-поле: `res.status`, `res.ok`, `req.url`,
    `server.port`;
  - значение, которое меняет сам объект своими методами, — тоже поле, только для чтения
    программе: части `URL` (`url.pathname`, `url.href`), `stream.locked`, `params.size`.
    Пишет в такое поле сам объект, своими методами; компилятор знает, что поле меняется, и
    не держит про него фактов после вызова. `URL` меняется методами: `url.setPathname("/x")`;
    `setHref`, `setProtocol`, `setHost`, `setHostname` и `setPort`, значение которых адрес может
    не принять, дают `Result<void, UrlError>` (литерал проверяется при сборке, и вызов с ним
    ничего не отдаёт). `url.searchParams.set(...)` меняет `url.href`, как в node: адрес и его
    параметры держат друг друга (кольцо, группа из двух объектов);
  - значение, которое меняется вместе с другим объектом, — метод: `res.bodyUsed()` (тело
    меняется, пока программа читает его поток `res.body`; поле пришлось бы обновлять из потока,
    то есть держать ссылку с потока на ответ — кольцо в каждом ответе), `controller.desiredSize()`
    (очередь меняет читатель).
  Поток тела `res.body` есть сразу, но лёгкий: своё состояние он строит при первом чтении
  (создавать полный поток на каждый ответ — в 6 раз дороже самого ответа).
- **У библиотеки нет членов «только для себя»** (решено 28 октября): ни `__`, ни `internal`,
  ни friend. Её объекты общаются открытым API, и любой открытый член безопасен, кто бы его ни
  позвал; что объект держит внутри — `private`. Связи строятся так: подписка
  (`url.searchParams.watch(...)`, параметры адреса сообщают адресу о переменах; `replace(text)`
  заменяет их разбором текста), фабрика с правом (`AbortSignal.withAbort()` отдаёт сигнал вместе
  с функцией отмены, как `Promise.withResolvers()`; конструктор сигнала закрыт, контроллер
  берёт сигнал так), выполнить вокруг (`event.dispatchOn(target, run)` — рассылка события;
  `event.immediateStopped`), скажи, а не спрашивай (`request.writeTo(conn)`,
  `Response.readFrom(conn, …)`, `headers.writeTo(conn)` — без соединения, которого программе
  взять неоткуда, их не позвать; операции ключа — методы ключа: `key.sign(...)`,
  `key.verify(...)`, `key.export(...)`…, `crypto.subtle` зовёт их), общая очередь (поток, его
  читатель и контроллер смотрят на одну очередь; `stream.locked` и `stream.disturbed` поток
  меняет сам). Методы, которые зовёт сам компилятор (`signal.onabort = f`,
  `addEventListener`, печать `Headers` и `URLSearchParams`), — `private` с обычными именами:
  компилятор — реализация языка, как и рантайм. Функции рантайма в коде библиотеки —
  `declare function netClose(...)` (имя в C — `tz_net_close`), встроенные функции компилятора —
  в модуле `tz:intrinsics`, который видят только модули библиотеки.
- **Классы как значения** (`const C = class {}`, передача класса в функцию, примеси) — вместе с
  декораторами.
- **Перегрузка** методов и конструкторов — как в C#: несколько тел с одним именем, вариант
  выбирает компилятор по типам аргументов ([overloads.md](overloads.md)).

## 7. Объединения и литеральные типы

```ts
interface Circle { kind: "circle"; r: double }
interface Square { kind: "square"; side: double }
type Shape = Circle | Square

function area(s: Shape) {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2
    case "square": return s.side ** 2
  }
}
```

- **Объединения объектов.** Сужение через `switch` / `if` по метке, `in` и `instanceof`. Метка
  (`kind`) одинакова у всей раскладки, поэтому хранится в описании, а не в объекте. Любая из этих
  проверок — одно сравнение указателя на описание. Общее поле одного типа (`s.name` у всех
  вариантов) читается без проверки.
- **Литеральные типы** (`type Dir = "up" | "down"`) внутри хранятся маленькими числами:
  сравнение — сравнение чисел, превращение в строку ничего не выделяет.
- **Объединения простых типов** (`string | int`) — значение с меткой типа (16 байт), сужение
  через `typeof`. Объединение двух числовых типов (`int | double`, `int | int32`) — ошибка:
  `typeof` у обоих даёт `"number"`, и различить их нельзя.
- **`switch` по метке объединения или по литеральному типу обязан разобрать все варианты**,
  иначе ошибка: «не разобран вариант "scroll"». Если пропуск задуман — `default: break`. Это
  касается только таких `switch`, не `switch` по обычным `int` и `string`.

## 8. `null`

`null` нет, как и сейчас. «Ничего» — только `undefined`: `x?: T`, `T | undefined`, `??`, `?.`.
`null` в коде — ошибка с подсказкой. В правилах для кода самого компилятора TypeScript написано
так же: «Use undefined. Do not use null.» Как разбирать `null` из JSON — решим вместе с JSON.

## 9. Словари

Объект — фиксированный набор полей, поэтому словарь с произвольными ключами — отдельный тип,
хеш-таблица.

- **`Record<string, T>` и `{ [key: string]: T }`** — хеш-таблица с синтаксисом объекта: `d[k]`,
  `d[k] = v`, `delete d[k]`, `k in d`, `Object.keys(d)`, `for...in`. У словаря `delete` и `in`
  — нормальные операции.
- **`Map` и `Set`** — как в JS. Внутри у словарей одна и та же хеш-таблица.
- **Порядок ключей** — всегда порядок добавления (в node ключи из цифр идут вперёд по
  возрастанию).
- **`Record<int, T>`** — ошибка: в JS ключ молча стал бы строкой. Для чисел есть `Map<int, T>`.
- **Отсутствующий ключ** читается как `T | undefined`, как элемент массива по недоказанному
  индексу.
- **Бородавок JS нет:** `"toString" in d` — `false`, `d["constructor"]` — `undefined`,
  `__proto__` — обычный ключ.
- **`Record<"math" | "art", int>`** — не словарь, а обычный объект `{ math: int; art: int }`.

## 10. Сахар

Как в JS:
- короткая запись `{ id, name }`;
- spread `{ ...user, name: "Anna" }` — новый объект; тип — итоговый набор полей; `undefined` из
  необязательных полей не копируется;
- деструктуризация: переименование, значения по умолчанию, остаток (`{ id, ...rest }` — новый
  объект), вложенная, в параметрах;
- `Object.keys` / `values` / `entries` — поля в том порядке, в каком объект печатается (порядок
  ключей литерала, как в node); у `values` тип элемента — объединение типов полей;
- печать — все поля (раздел 6).

Ключ в квадратных скобках (`{ [key]: v }`, `u[k]`) должен быть известен при компиляции:
константа или литеральный тип (`k: "name" | "email"`). Произвольная строка — ошибка (нужен
`Record`); tsc в strict-режиме тоже не даёт `u[k]` с `k: string`.

### Кортежи

`[string, int]` — массив фиксированной длины, где у каждого места свой тип. Нужны для пар из
функций, `Object.entries` и обхода `Map`.

```ts
function splitName(full: string): [string, string] { ... }
const [first, last] = splitName("Ann Lee")
const t: [string, int] = ["Ann", 30]
t[1]                      // tz: ок, читается напрямую
t.push(5)                 // tsc: ок (из пары стала тройка). tz: ошибка — длина фиксирована
t[j]                      // tz: ошибка — только номер-константа или деструктуризация
const arr: (string | int)[] = t   // tz: ошибка, подсказка: [...t]
```

Внутри кортеж — как объект с полями `0`, `1`, ...: ссылка, как в JS. Если он сразу разобран,
компилятор может обойтись без выделения памяти.

### `for...in`

По массиву — ошибка: в JS индекс там строка (`i + 1` даёт `"01"`). Подсказка: `for...of`,
`for (let i = 0; ...)` или `forEach`. По объекту и словарю `for...in` перебирает ключи.

## 11. Память: циклы без сборщика

Память освобождается подсчётом ссылок, как сейчас. Цикл ссылок (дерево с `parent`, подписчик,
который держит объект, держащий подписчика) подсчётом ссылок не освобождается. Сборщика циклов,
который время от времени обходит память, не будет. Вместо него — три слоя.

**Какие типы циклические.** Компилятор строит граф «поле типа A может держать объект типа B»
(с элементами массивов, значениями словарей, захватами замыканий и наследниками). Тип, который
через стрелки возвращается к себе, может образовать цикл. Поле, которое после создания объекта не
меняется, цикл не замыкает: оно указывает только на объекты, созданные раньше. Остальные типы —
обычный подсчёт ссылок, без всяких добавочных затрат.

**Слой 1, при компиляции: структура не выходит наружу.** Если ни один объект структуры не
вернули, не положили в глобальную переменную и не сохранили в объект снаружи, при выходе из
функции она освобождается целиком. То же при перезаписи переменной, которая одна держит
структуру.

**Слой 2, при компиляции: обратная ссылка в то, чем объект владеет.** `Dialog` создаёт свою
кнопку и никому её не отдаёт, а замыкание в кнопке ссылается на `Dialog`. Компилятор доказывает,
что кнопка не переживёт `Dialog`, и ссылку замыкания на `Dialog` не считает.

**Слой 3, во время работы: группы.** Это вариант по умолчанию для всего остального.
- Объекты циклических типов, которые связали друг с другом, образуют группу с одним счётчиком
  внешних ссылок. Ссылки внутри группы не считаются.
- При связывании объектов из разных групп группы сливаются. Обратно группы не делятся.
- Внешних ссылок 0 — вся группа освобождается сразу. Поведение как в JS: узел, который держат
  снаружи, держит всю структуру.
- Ссылки на «вечные» объекты (глобальные переменные, которые не переприсваивают) не считаются и
  группы не сливают.
- Цена: +16 байт у объекта циклического типа (указатель на группу и ссылка на следующего члена
  группы) и проверка «та же группа?» при записи ссылки в поле такого объекта.

**`WeakRef` — по желанию программиста.** `parent?: WeakRef<TreeNode>` не держит родителя, и
тогда части структуры освобождаются по отдельности. В tz слабая ссылка становится `undefined`
ровно в момент, когда объект умер (в node — когда-нибудь, при сборке мусора V8).

**Известный риск: отцепленные части держатся до смерти всей группы.** Например, игроки на время
партии ссылаются друг на друга через `opponent`, и за день все игроки сервера сливаются в одну
группу. Программа не падает, но память растёт. Лечится `WeakRef` на такой связи. Найти её помогает
отладочный режим (ниже).

**Освобождение больших групп — в фоне.** Основной поток помечает группу мёртвой за O(1), с этого
момента `WeakRef` на её объекты даёт `undefined`. Сами объекты освобождаются так:
- группы меньше ~10 000 объектов — сразу на месте (микросекунды);
- большие — в фоновом потоке. Без async это один поток, который создаётся при первой надобности
  и потом спит до следующей работы. С параллельным async — задачи с низким приоритетом в пуле
  рабочих потоков рантайма.
- Фоновый поток освобождает объекты со счётчиком 1 (их держит только мёртвая группа). Общие
  объекты (счётчик больше 1) он возвращает потоку-владельцу: счётчики не атомарные.
- Аллокатору для этого нужны списки «освобождено чужим потоком» у каждой страницы, как в
  mimalloc. Для параллельного async они понадобятся и так.
- Если очередь на освобождение слишком велика, основной поток помогает или ждёт.

Замеры на нашем аллокаторе (узел 48 байт со строкой, узлы разбросаны по памяти): 100 000 узлов —
0,3 мс, миллион — 33 мс, десять миллионов — 345 мс. Поток: создать — ~40 мкс, разбудить — ~2 мкс,
~17 КБ памяти.

**Отложено 25 октября** (шаг 10): пока любая группа освобождается сразу, в потоке, где умерла.
Что мешает: чтобы фоновый поток отличал объекты, которые держит только мёртвая группа, от тех, что
надо вернуть владельцу, каждое освобождение поля должно проверять, в фоне ли оно (это либо
замедлит весь код, либо потребует вторых функций освобождения для всех типов). А блоки, которые
освободил чужой поток, аллокатор возвращает через владельца по одному, с тем же промахом кэша, так
что владелец почти ничего не выигрывает, пока аллокатор не забирает страницу целиком. Другой путь,
который обсуждали: освобождать большую группу частями по ~10 000 объектов в том же потоке — при
выделении памяти и на оборотах цикла событий; работа та же, паузы — доли миллисекунды.

**Отладочный режим для тестов** (не в рабочем exe):
- изредка обходит группы и сообщает: «группа `Player`: 9 800 из 10 000 объектов недостижимы, их
  держит `Player.opponent`, строка 23»;
- проверяет доказательства слоёв 1 и 2 во время работы. Ошибка в таком доказательстве означала
  бы обращение к освобождённой памяти, а не утечку;
- `TZ_CHECK_LEAKS=1` показывает оставшиеся группы с именами типов.

## 12. Отложено

- `Partial`, `Pick`, `Omit`, `keyof` в обобщённых функциях, ограничения `T extends {...}` —
  вместе с generics.
- Классы как значения, class-выражения, примеси — вместе с декораторами.
- `WeakMap`, `Object.assign`, `Object.freeze`, `structuredClone` — по мере надобности.
- Группы, которые видят несколько потоков (атомарные счётчики, слияние), — вместе с параллельным
  async.

## План реализации

На каждом шаге: тесты `tests/run` (где поведение совпадает с JS — с `// same-as-node`), ошибки в
`tests/errors`, прогон с `-O0` и `-O2` под `TZ_CHECK_LEAKS=1`, обновление README. Для замеров
скорости в `bench` добавить программы на объектах (binary-trees, n-body) рядом с версиями на Go.

1. **Типы объектов и литералы** (сделано). Синтаксис `{ a: T; b?: U }`, `interface`, `type`;
   литералы, в том числе короткая запись; чтение и запись полей; необязательные поля; вложенные
   объекты, массивы объектов, объекты в замыканиях. Описания раскладок в exe, выделение памяти
   через `tz_obj_alloc`, освобождение полей, `==`, `Obj | undefined` как ссылка или ноль. Точные
   типы и ошибки на лишние поля. Тип полей литерала — из ожидаемого типа на месте литерала.
   Печать как в node.
2. **Сахар** (сделано). Вывод типов полей литерала по тому, куда объект попадает дальше. Spread,
   деструктуризация объектов, `Object.keys` / `values` / `entries`, `for...in` по объектам;
   ошибки на `in` / `delete` для необязательных полей и на `for...in` по массивам. Кортежи.
3. **Классы без наследования** (сделано). Поля с начальными значениями, конструктор, параметры-свойства,
   методы, `this`, `new`, `static`, `private` / `#x` / `protected`, `instanceof`, классы по
   имени. Правило инициализации полей, ошибки на `x!`, `get` / `set`, замену метода. Метод как
   значение с привязкой к объекту, стрелки в полях. Методы в литералах.
4. **Наследование и интерфейсы** (сделано). `extends` / `super` / `override` / `abstract`, `implements`,
   поля родителя в начале объекта, таблицы методов и прямые вызовы там, где метод никто не
   переопределяет; номера классов для `instanceof`; интерфейсы с полями. Ошибка на вызов
   переопределённого метода из конструктора родителя. Запись через более широкий тип на этом
   шаге запрещена всегда (строго).
5. **Запись через более широкий тип — проверка по всей программе** (сделано). Снимает строгость шага 4:
   `Dog[]` в `Animal[]`, сужение типа поля в наследнике, `readonly` в изменяемое — разрешены,
   если записи нет.
6. **Объединения** (сделано). Объединения в системе типов шире `T | undefined`, литеральные типы,
   объединения объектов с сужением, полнота `switch`, объединения простых типов с меткой,
   сужение `typeof`.
7. **Словари** (сделано). Хеш-таблица в рантайме с порядком добавления; `Record` и `{ [k: string]: T }`;

9. **Циклы: слои 1 и 2** (сделано). Анализ выхода структуры из функции и владения, отладочная проверка
