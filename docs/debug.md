# Отладка

Решено 1–2 ноября 2026 (progress.md, пункт 0.2, вопросы В1–В3): стек при падении — со строками
`.tz` всегда; отладчик (точки останова, шаги, переменные) — для сборки `tz build --debug`;
переменные видны в отладчике так же, как их печатает `console.log`: строка — текстом, массив —
элементами, объект — полями. Пока только Windows (CodeView и .pdb); Linux (DWARF и
pretty-printers для gdb/lldb) — вместе с переносом на Linux (пункт 0.4).

## Коротко

- `tz build app.tz` пишет рядом с `app.exe` файл `app.pdb`: таблицу строк `.tz` и функции.
  Exe от этого не растёт (+3,5 КБ кода печати стека), сборка — на ~70 мс дольше, .pdb — около
  4–5 МБ. `tz run` удаляет и exe, и .pdb.
- Паника, переполнение стека и внутренняя ошибка печатают стек со строками `.tz`
  ([errors.md](errors.md), раздел 9).
- `tz build --debug app.tz` — без оптимизаций (как `-O0`) и с переменными, их типами и видами для
  отладчика (`tz.natvis` внутри .pdb).
- VS Code: F5 на файле `.tz` (нужно расширение C/C++ от Microsoft). Visual Studio: открыть exe.

## 1. Стек при падении

```
panic: Maximum decimal size exceeded
    at deeper (D:\app\main.tz:15)
    at middle (D:\app\main.tz:20)
    at new Counter (D:\app\main.tz:27)
    at D:\app\main.tz:32
```

- Строки берутся из `.pdb` рядом с exe через DbgHelp из System32; она грузится только при падении,
  в отдельном потоке (так стек печатается и при переполнении стека). Печать — ~15 мс.
- Видны только функции программы и библиотеки tz (файлы `.tz`), в том числе встроенные
  оптимизатором; функции рантайма на C — нет. Верхний уровень программы — без имени. Одинаковые
  строки подряд (рекурсия) — одной строкой и `[previous line repeated N more times]`; всего не
  больше 24 строк.
- Без `.pdb` рядом — адреса и подсказка `(no app.pdb next to app.exe: only addresses)`: на сервер
  .pdb копируется вместе с exe, если нужен стек со строками.
- После `await` стек начинается с продолжения async-функции: кто её ждёт, не видно (как у Go и
  Rust без отладчика).
- Внутренняя ошибка (обращение не по адресу и т. п.) — `panic: internal error: access violation`,
  стек и код 2: это ошибка tz, не программы.

## 2. `tz build --debug`

- Без оптимизаций: каждая переменная лежит в своей ячейке, шаги идут по строкам.
- Переменные, параметры, `this`, захваченные замыканием переменные (и изменяемые из него — через
  коробку), глобальные переменные модуля, переменные async-функций (после `await` — из кадра
  сопрограммы).
- Типы tz описываются по их раскладке в памяти ([debug_types](../compiler/lower/debug_types)),
  а виды — [tz.natvis](../editors/debug/tz.natvis), который линковщик кладёт в .pdb (`/natvis`).
- `tz run --debug` тоже работает, но отладчику нужен exe: удобнее `tz build --debug`.

## 3. VS Code

Нужно расширение tz ([editors/vscode](../editors/vscode/README.md), версия 0.5 и новее) и
расширение C/C++ от Microsoft (`ms-vscode.cpptools`): его отладчик (`cppvsdbg`) читает .pdb.

- F5 на открытом файле `.tz` без launch.json — собрать его `tz build --debug` в
  `%TEMP%\tz-debug\` и запустить под отладчиком. Точки останова ставятся в файлах `.tz` как
  обычно (F9 или щелчок слева от номера строки).
- launch.json, если нужны аргументы, переменные окружения или рабочий каталог:

  ```json
  {
    "version": "0.2.0",
    "configurations": [
      {
        "type": "tz",
        "request": "launch",
        "name": "Debug the .tz file",
        "program": "${workspaceFolder}/main.tz",
        "args": ["--port", "3000"],
        "env": { "LOG": "1" },
        "cwd": "${workspaceFolder}"
      }
    ]
  }
  ```

- Ошибки сборки — в Output, канал TypeZero Debug; сессия тогда не начинается.

## 4. Как видны значения

| Тип tz | В отладчике |
|---|---|
| `int`, `int32`, `uint8`… | число (тип — `__int64`, `int`, `unsigned char`: имена C++, своих у простых типов в .pdb нет) |
| `double` | число |
| `boolean` | `true` / `false` |
| `string` | `"текст"` (и кириллица, и строки из кусков: `"abc" + "def"`), `length` |
| `T[]` | `{ length=3 }`, раскрывается в элементы |
| объект, класс | `{name="Ann" age=42}`, раскрывается в поля по именам (поля предков — тоже) |
| `T \| undefined` | `undefined` или значение; объект — указатель (`<NULL>` — `undefined`) |
| `Result<T, E>` | `Ok(12)` / `Err(...)` |
| `Map`, `Record`, `Set` | `{ size=2 }`, раскрывается в пары ключ — значение / элементы |
| `string \| int` и другие объединения | значение того варианта, что лежит сейчас |
| `"GET" \| "POST"` | `"GET"` |
| функция | `function "name"` |
| `decimal` | `125e-1` |

Пока не так, как хотелось бы: объединение объектов (`Circle | Square`) показывается как `object`,
без полей (кто именно лежит, знает только описание типа во время работы); в выражениях окна
Watch — синтаксис C++, не tz; у async-функции виден ещё `__coro_frame` — кадр сопрограммы LLVM.

## 5. Visual Studio

`devenv /debugexe app.exe` или File → Open → Project/Solution → `app.exe`, затем F5. Visual Studio
берёт .pdb и natvis из него так же, как VS Code. Проверка видов natvis без рук —
[editors/debug/vs-check.ps1](../editors/debug/vs-check.ps1): запускает программу, подключает
отладчик Visual Studio через автоматизацию (EnvDTE) и печатает переменные функции, на которой
программа остановилась (`debugger`).

## 6. Как устроено

- [DebugInfo](../compiler/lower/debug_info): единица компиляции, файлы (у библиотеки — настоящий
  путь, чтобы отладчик открыл исходник), функция на каждое тело (`beginFunction`, верхний
  уровень — `<top level>`), место у каждой инструкции: оператор и выражение ставят свою строку
  (в пределах строки — одно место: иначе «шаг внутрь» останавливается на кусках строки),
  `BlockStmt::end` — закрывающая `}`. В конце `repair()`: инструкции без места или с местом чужой
  функции получают место соседа.
- Переменные — `declare()` у ячейки (`FunctionFrame::createLocal`, `this`, захваты замыканий,
  глобальные). Параметр-структура больше 8 байт (строка, `T | undefined` с флагом, объединение)
  объявляется как переменная, не как параметр: отладчик Windows считает, что такие параметры
  переданы по ссылке, и читает не то (проверено).
- Линковщик: `/debug /opt:ref /opt:icf /pdbaltpath:%_PDB%` — без `/opt:ref` и `/opt:icf` `/debug`
  не выкидывает неиспользуемый код (exe рос с 1,08 до 2,8 МБ); `%_PDB%` — в exe только имя .pdb,
  без пути машины, где собирали. С `--debug` ещё `/natvis:tz.natvis`.
- Печать стека — [stack_trace.c](../runtime/core/output/stack_trace.c): раскрутка
  `RtlVirtualUnwind`, имена и строки — `SymFromAddrW` / `SymGetLineFromAddrW64`, встроенные
  кадры — `SymQueryInlineTrace`.
- Тесты: `run/panic_stack`, `run/stack_overflow`, `cli/debug` (что лежит в .pdb, через
  llvm-pdbutil).
