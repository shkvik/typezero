# Движок для редактора и ИИ: `tz lsp`, `tz mcp`, `tz query`

Решено 29 октября 2026 года. Шаги 1 (ошибки в редакторе), 2 (ИИ), 3 (замер) и 4 (редактор:
наведение, переход, ссылки, дополнение, переименование) сделаны 29 октября; из 5 и 7 — первые
части (уровни проверки, ответы ИИ из памяти, ускорение загрузки), 6 не начат (tmp/progress.md,
раздел 7).
Схема с переключателем «сейчас / шаг 1 / шаг 2 / цель» — [tmp/design/lsp-architecture.html](../tmp/design/lsp-architecture.html).

## Коротко

- **Один движок внутри `tz.exe` (C++)** и три входа в него: редактор — `tz lsp` (протокол LSP),
  ИИ-агент — `tz mcp` (протокол MCP), люди и скрипты — `tz query`, `tz map`, `tz context`,
  `tz impact`. Код разбора и проверки — тот же, что у `tz build`.
- **Все входы читают одни записи модулей**, которые считает компилятор: символы, типы (и
  выведенные), вызовы, импорты, ссылки, места в исходнике, ссылки на разделы docs. Ключ записи —
  хеш текста модуля и версия tz.
- **Цель — репозиторий на миллиард строк на обычном SSD**: движок не грузит всё, считает по
  запросу то, что нужно открытым файлам и запросу ИИ, помнит результаты на диске и
  пересчитывает только то, что зависит от правки.

## Протоколы

- **LSP** — стандарт: JSON-RPC через stdin / stdout, VS Code запускает `tz.exe lsp` (по процессу на
  окно). Клиент в расширении — `vscode-languageclient` (MIT) в third_party. Свои возможности tz —
  своими запросами в том же протоколе (`tz/...`).
- **JSON, не двоичный формат.** Замер в node: правка — 0,001 мс, 1000 ошибок — 0,4 мс, 5000
  вариантов автодополнения — 0,9 мс при бюджетах 50–300 мс; VS Code и сам передаёт данные между
  своими процессами в JSON. Передача — тонкий отдельный слой: если замер когда-нибудь покажет её в
  узком месте, её заменяют, не трогая ядро.
- **MCP** — для ИИ-агентов; в этом репозитории подключается в `.mcp.json`.

## Что отвечает ИИ

- `map --budget N` — обзор проекта в заданный объём: модули, экспорт с полными типами,
  зависимости; часто используемое раскрыто подробнее.
- `context <символ | файл:строка> --budget N` — всё про одно место: тело, сигнатуры того, что оно
  использует, кто вызывает, тесты, разделы docs.
- `query` — определение, все места, кто вызывает, тип в точке; `impact <символ>` — что затронет
  правка.
- **Проверка правки без записи**: ИИ присылает изменение, компилятор проверяет его в памяти и
  отдаёт ошибки как данные (файл, начало и конец места, вид, текст, заметки).
- **Памятка по языку** — [ai.md](ai.md), подкладывается к ответам.
- Описаний, написанных ИИ, в первой версии нет. Позже — только с хешем описываемого текста и
  пометкой «не проверено компилятором». «Зачем» берётся из docs (связь «символ → раздел»), в коде
  комментариев нет.
- Генераторов кода (`generate service` и подобных) нет: из правок только проверяемые механические —
  переименование и перенос.

## Требования (цель)

| Что | Цель |
|---|---|
| Подсказка, ответ на запрос ИИ | меньше 50 мс |
| Ошибки текущего файла, проверка правки ИИ | меньше 300 мс |
| Запуск с кэшем | секунды |
| Первый запуск без кэша, 1 млрд строк | ~10 мин на 16 ядрах; 1–2 мин после ускорения |
| Память движка | 2–4 ГБ при любом размере репозитория |
| Записи модулей / индексы на диске (1 млрд строк) | 2–4 ГБ / 5–10 ГБ |

Сейчас (замер 29 октября на сгенерированных проектах): проверка ~100 тыс. строк в секунду на
ядро, 0,85 КБ памяти на строку — полная перепроверка укладывается в 300 мс примерно до 30 тыс.
строк и годна для редактора примерно до 200–300 тыс.

## Устройство (цель)

- **Ядро запросов**: каждый результат (разбор файла, запись модуля, ошибки функции, модуля,
  программы) считается по запросу и помнит, от чего зависит; правка сбрасывает только зависящее.
- **Ранняя остановка**: правка в теле — перепроверка одной функции; запись модуля не изменилась —
  зависящие модули не трогаем. Типы экспорта выводятся из тел (аннотации не требуем), поэтому
  после правки выведенная сигнатура сравнивается со старой.
- **Три уровня проверок**: функция и модуль — сразу; вся программа (параллельность, карты
  событий, копии обобщённых функций, переполнения) — в фоне из записей; целиком — в `tz build`.
  Правило для языка: любая проверка «на всю программу» должна складываться из записей модулей.
- **Рабочий набор**: в памяти — открытые файлы и записи их зависимостей; редкое выбрасывается.
- **Планировщик**: запросы редактора и ИИ вытесняют фон; любую работу можно отменить.
- **Диск**: записи модулей и индексы — в LMDB (C, OpenLDAP Public License) за интерфейсом
  `get(хеш) / put(хеш, байты)`; формат записи — свой, с версией, читается через `mmap` без
  разбора. Кэш одноразовый: его можно удалить и пересчитать. Только локальный диск, короткие
  читающие транзакции, отображение только для чтения, запись пачками.
- **Слежение**: при запуске — изменения по USN-журналу NTFS (Linux — сохранённое состояние, как
  fsmonitor); дерево каталогов не обходится; переключение веток не пересчитывает уже знакомые
  хеши.
- **«Вся программа»** — одна точка входа или пакет из `tz.json`, а не весь репозиторий.

4. **Редактор полностью — сделано** (кроме нового разбора недописанного кода: ответы идут из
   последней проверки). Наведение, переход к определению, все ссылки, автодополнение,
   переименование — на тех же записях. Как устроено — «Шаг 4: как сделано» ниже.
5. **Ядро запросов** — записи по одному модулю, ранняя остановка, уровни, рабочий набор, фон.
   Сделаны первые части: два уровня проверки в редакторе (быстрый без анализа всей программы,
   потом полный — в фоне), ответы ИИ из записей последней проверки, пока файлы не менялись.
   Проверки по одному модулю и ранней остановки нет — это переделка самой проверки (см. «Шаги

6. **Диск** — записи и индексы в LMDB, слежение по журналу. Не начато: без записей по одному

7. **Ускорение** разбора и проверки в 5–10 раз на ядро (плотные массивы, имена числами, память
   кусками). Сделаны точечные ускорения загрузки (−15…45%) и ответов; главное — впереди.

Позже: общий кэш записей с CI по хешу; поиск по смыслу внутри инструмента; разбор только
изменённого куска файла, зависимости по полям, ответы старым результатом, пока считается новый.

## Шаг 1: как сделано

- **Каждая проверка — дочерний процесс** `tz lsp --check <запрос> <ответ>`: сервер пишет в файл
  запроса точку входа и текст открытых файлов, ребёнок проверяет программу (проходы до
  `OverflowPass`, как `tz build` до LLVM) и пишет в файл ответа ошибки как данные и список файлов
  программы. Запуск стоит ~12 мс. Почему не проверка внутри сервера: недописанный код может
  уронить компилятор — падает ребёнок, а сервер показывает «tz stopped while checking this
  program… this is a bug in tz» и живёт дальше; устаревшую проверку можно по-настоящему
  остановить (процесс убивается); память после проверки возвращается системе; глобальные таблицы
  типов не надо чистить. Внутрь сервера проверка переедет вместе с ядром запросов (шаг 5).
- **Что проверяется.** Файл под `tz.json` с `main` — вместе с этим `main`; если `main` его не
  импортирует — отдельно; файл без `tz.json` — сам по себе. Ошибки приходят и для файлов
  программы, которые не открыты. Правка открытого файла перепроверяет все программы, где он
  есть; изменение файла на диске (VS Code сообщает о `*.tz` и `*.json`) — тоже; `tz.json` —
  заново решает, что чем проверять.
- **Файл самой библиотеки tz** (`library/http/fetch.tz` в исходниках tz; 30 октября) — не
  программа: в нём `declare function` и `tz:intrinsics`, которые программе нельзя. Загрузчик
  узнаёт такой файл по месту (папка `library/` с `CMakeLists.txt` и `core/intrinsics.tz`) и
  проверяет его как встроенный модуль, которым он и есть (`tz:fetch`), — один, без программы
  вокруг. Вся библиотека в такой проверке берётся из этого же дерева исходников, а не из
  `bin/lib`, с текстом из редактора: правка в `http.tz` сразу видна при проверке `fetch.tz`.
  Имя буфера остаётся именем модуля (по нему компилятор узнаёт `node:stream` и др.), а файл
  каждого буфера записан отдельно (`Module::bufferFiles`) — ошибка встаёт в свой файл и строку,
  и в части модуля (`stream_duplex.tz`), и в `http.d.tz`. Связь файла и модуля —
  `LibraryFiles` (`compiler/load/library_files/`); новый файл библиотеки — новая строка там,
  иначе тест `cli/lsp` (открывает каждый файл библиотеки и ждёт ноль ошибок) упадёт.
- **Ошибки как данные**: файл, строка, начало и конец места (столбцы — в единицах UTF-16, как
  считает редактор; конец — конец слова, строки в кавычках или знака), вид (ошибка,
  предупреждение), текст, заметки — `relatedInformation` той ошибки, за которой идут. Место
  внутри встроенного модуля tz (`tz:http`…) пишется в текст, а ошибка ставится в начало точки
  входа.
- **Замер** (29 октября, проверка вместе с запуском): маленькая программа и программа с
  `node:fs` — 12–40 мс; один `EventEmitter` — 36 мс (3 круга карт событий); две строки с
  `fetch` или `tz:http` — ~450 мс, из них ~410 мс — `OverflowPass` (пределы целых по всей
  программе, вместе с сетевой частью библиотеки на tz). Отсюда уровни проверки (шаг 5): сначала
  быстрая проверка без `OverflowPass`, потом полная. С 30 октября `OverflowPass` здесь — 135–160 мс
  (D10, «Шаги 5–7»).

## Шаг 2: как сделано

- **Записи модулей** (`compiler/knowledge/`): после проверки `KnowledgePass` проходит AST, где
  проверка уже разрешила имена, и пишет на модуль: путь, хеш текста (xxh3), версию tz, строки,
  импорты; **символы** — функции, классы и их поля, конструкторы и методы, типы, `enum`,
  переменные модуля: вид, имя, сигнатура с выведенными типами, место имени и всего объявления,
  экспорт; **ссылки** — на какой символ, из какого символа (или кода модуля), вызов ли, место;
  **типы в точках** — имя и тип каждого имени в коде, и локальных тоже. Ключ символа —
  `модуль#Класс.член` (`vec.tz#Vec.add`, перегрузки — `/2`), а не место: запись модуля не
  зависит от строк других модулей — это нужно ядру (шаг 5) для ранней остановки. Копии
  обобщённых функций и классов приводятся к исходному объявлению. `tz query records` печатает
  записи.
- **Ответы** (`tz map` / `context` / `query` / `impact`, текстом и `--json`) — по записям; бюджет
  в токенах (~4 знака): в `map` первыми идут экспорт и самое используемое, в `context` исходник
  берёт не больше половины. Разделы docs — строки `docs/*.md`, где имя стоит в обратных кавычках
  (`Класс.член` раньше имени), с заголовком раздела; тесты — файлы `tests/**/*.tz`, где имя
  встречается словом, с пометкой «by text». Каталог с `docs` ищется вверх от проекта.
- **Цель**: `имя`, `Класс.член`, `файл.tz:строка` (самое внутреннее объявление вокруг строки,
  а в коде модуля — то, что строка использует) или `файл.tz:строка:столбец` (объявление или
  ссылка в этом месте; для `query type` — тип имени). Программа — `--entry`, иначе `tz.json`
  файла из цели или текущего каталога; файл, который `main` не импортирует, — своя программа.
- **`tz mcp`** — MCP через stdin / stdout (JSON-RPC, сообщение в строку): `initialize`,
  `tools/list`, `tools/call`. Каждый вызов инструмента — дочерний `tz` (как проверка в
  `tz lsp`: падение не роняет сервер, память возвращается); `check_edit` берёт файл и его новый
  текст или замену `old` → `new` (ровно одно вхождение), проверяет программу с этим текстом в
  памяти (`tz lsp --check`) и отдаёт ошибки `файл:строка:столбец: текст` с заметками.
  `language_card` — `ai.md` рядом с `tz.exe` (сборка кладёт его туда) или `docs/ai.md`.
- **`.mcp.json`** этого репозитория запускает `node editors/mcp/tz-mcp.cjs`: тот копирует
  `build/dev/bin/tz.exe`, `lib` и `ai.md` во временный каталог и запускает `tz mcp` оттуда —
  иначе работающий сервер держал бы `tz.exe`, и сборка не могла бы его заменить.
- Замер: ответ на маленькой программе — 20–40 мс, на тесте с `fetch` — ~600 мс (почти всё —
  проверка, см. шаг 1).

## Шаг 3: замер

Генератор `bench/scale/gen.py` пишет программу из модулей по ~500 строк (тип записи, тип ошибки,
класс с методами, функции с циклами, `Result` и вызовами в импортированные модули; модуль `i`
импортирует `2i+1`, `2i+2`, `2i+3`), `bench/scale/measure.ps1` меряет проверку редактора
(`tz lsp --check`), `tz map` и записи. 29 октября, 32 ядра, проверка — одно ядро, файлы уже в
кэше диска:

| Строк | Проверка | Память | `tz map` (проверка + записи + ответ) |
|---|---|---|---|
| 10 тыс. | 0,1 с | 16 МБ | 0,1 с |
| 100 тыс. | 0,2 с | 102 МБ | 0,4 с |
| 300 тыс. | 0,7 с | 268 МБ | 1,0 с |
| 1 млн | 2,6 с | 0,83 ГБ | 3,7 с |
| 3 млн | 10,2 с | ~2,4 ГБ | 12,6 с |
| 10 млн | ~55 с | ~8 ГБ | 63 с |

- Время растёт быстрее строк: ×3 строк — ×3,9 времени, ×3,3 — ×5,4; память — ~0,8 КБ на строку.
  Первая проверка только что записанных файлов втрое медленнее (10 млн — 166 с): антивирус
  смотрит каждый файл при первом чтении.
- Записи в JSON — ~370 байт на строку (больше всего — типы каждого имени); при 10 млн строк дамп
  `tz query records` не уложился в 20 ГБ памяти — для диска нужен свой двоичный формат (шаг 6).
- Маленькие программы упираются не в размер, а в библиотеку: две строки с `fetch` — ~450 мс,
  из них ~410 мс — `OverflowPass` по сетевой части библиотеки (лог сервера теперь пишет время
  каждого прохода и число кругов). Прежний замер «`EventEmitter` — 1,1 с» был через
  `--explain-parallel`, то есть с анализом параллельности; сама проверка — 36 мс.
- Задачи для ИИ — 6 вопросов по `library/http/fetch.tz` из коммита 84d11d3, с инструментом и
  без; итог — ниже, в «Шаг 3: задачи для ИИ».

## Шаг 3: задачи для ИИ

Шесть вопросов по `library/http/fetch.tz` (2700 строк) и тесту `stream_bodies.tz` из коммита
84d11d3: кто вызывает `bodyStream` и во что он превращает ошибку; что возвращает `fetch`, когда
падает поток тела; все вызовы `requestError`; тип элементов `ReadableStream.values()`; где тест
зовёт `Response.stream`; что затронет правка `plainInit`. Каждый вопрос — два агента (Sonnet):
с `tz context` / `query` / `impact` и только с поиском и чтением файлов. 29 октября:

| | Вызовов инструментов | Токенов (из них своих, сверх ~42 тыс. общих) | Время | Верно |
|---|---|---|---|---|
| с инструментом | 16 (2–3 на вопрос) | 264 тыс. (~12 тыс.) | 94 с | 6 из 6 |
| поиск по тексту | 21 (3–4 на вопрос) | 270 тыс. (~18 тыс.) | 76 с | 5 из 6 |

- С инструментом — на четверть меньше вызовов и примерно на треть меньше своих токенов; одна
  ошибка поиска по тексту (строки вызовов `bodyStream` верны, а имена двух окружающих методов —
  нет: `Request.readFrom` и конструктор `Response` вместо `Request.stream` и `Response.stream`)
  инструменту не грозит — он знает, где кончается метод. В вопросе о влиянии правки инструмент
  сам дошёл до шести мест в тесте, поиск — остановился на `fetch`.
- Быстрее не стало: каждый вызов — полная проверка программы с библиотекой (~0,6 с), а в одном
  вопросе агент с инструментом всё равно читал файл. На одном файле в 2700 строк поиск ещё
  справляется; разница должна расти с размером и числом файлов — проверить на настоящем большом
  проекте, когда он будет.
- Что поправлено по итогам: ссылки внутри аргументов `new` (их переносит проверка), копии
  обобщённых функций и методов (по месту в исходнике), функции-аргументы, проверенные копией
  (по объемлющему объявлению); `map` больших программ — модули по важности и сводка остальных;
  индексы вместо полных проходов (на 300 тыс. строк `map` — 1 с вместо 12).

## Шаг 4: как сделано

- Проверка в `tz lsp --check` по флагу `knowledge` кладёт в ответ записи модулей
  (`KnowledgeJson`: тот же формат, что `tz query records`; у встроенных модулей — только
  символы), сервер держит их на каждую программу (`Knowledge`) и отвечает по ним сразу, не
  дожидаясь новой проверки (`compiler/lsp/lsp_features/`).
- **Наведение** — сигнатура символа (с выведенными типами), тип локального имени или тип имени
  в точке. **Переход к определению** и **все ссылки** — по символам и по локальным: записи теперь
  знают и локальные переменные и параметры (место объявления и все использования, у копий
  обобщённых функций — по месту в исходнике), импорты и списки `export { … }` — тоже ссылки.
  Определение во встроенном модуле открывает его копию рядом с `tz.exe` (`lib/`).
- **Дополнение** после точки — члены типа имени перед точкой (классы — поля и методы с
  наследованными, объекты — поля, строки, массивы, `Map`, `Set`, `Result` — их методы; `this.` —
  члены своего класса); без точки — локальные функции, символы модуля, то, что модуль
  использует, и ключевые слова. Текст с только что набранной точкой не разбирается — поэтому
  ответ из последней удачной проверки.
- **Цвета по смыслу** (semantic tokens): классы, типы, `enum`, функции, методы, поля и переменные
  — по тому, что знает проверка, а не по грамматике TypeScript; у встроенного —
  `defaultLibrary`, у `const` и `readonly` — `readonly`. Метка ставится, только если в тексте на
  этом месте стоит то же имя (записи могут отставать от набора на одну проверку); после
  проверки сервер просит редактор перекрасить файл.
- **Переименование** — объявление и все ссылки, но только места, где в тексте стоит старое имя
  (импорт `import { Vec as V }` меняется в `Vec`, а `V` — нет); встроенное не переименовывается;
  новое имя проверяется. Ошибки после переименования показывает обычная проверка.

## Шаги 5–7: что сделано и что дальше

- **Уровни (шаг 5).** `BuildOptions::overflow`: проверка без `OverflowPass` — уровень «быстро»;
  `tz lsp` сначала шлёт её ошибки (`level: 1`), потом в фоне — полную (`level: 2`), а ошибки,
  которые находит только полная, держит, пока идёт следующая быстрая (без мигания). Программа с
  `fetch`: ошибки через ~45 мс вместо ~450. Ответы `tz map` / `context` / `query` / `impact` —
  тоже без `OverflowPass`.
- **Ответы ИИ из памяти.** `tz mcp` держит записи программы (`tz query records --json --brief`:
  символы, ссылки, ошибки, без типов в точках) и отвечает из них, пока у файлов программы те же
  время и размер; вопросы о месте со столбцом (тип, локальная переменная) идут дочерним `tz`.
  100 тыс. строк: первый ответ — 0,8 с, следующие — 5 мс; 1 млн — 11 с и 40 мс.
- **Записи для редактора** — типы в точках и локальные только у открытых файлов (на 100 тыс.
  строк они — 90% записей).
- **Загрузка (шаг 7).** Модули не лексируются заново ради `process.stdout` и т. п., если в тексте
  нет `std`; имена глобальных классов библиотеки — по таблице, а не перебором; проверка файлов
  при импорте — один раз на путь. 1 млн строк: загрузка 1,2 → 1,0 с; 3 млн: 5,4 → 3,0 с, полная
  проверка 9,8 → 7,3 с; рост стал почти линейным.
- **`OverflowPass` быстрее (D10, 30 октября).** Программа из двух строк с `fetch`: 400 → 135 мс,
  с `tz:http` — 365 → 160 мс; вся проверка — 150–180 мс (бюджет 300). Время уходило на два места
  библиотеки (`parseIPv6` и `punycode` в `url.tz` — 300 из 400 мс): вложенные циклы, и каждый
  внешний проход заново гонял внутренние до неподвижной точки, и так в каждом из 12 кругов.
  Два запоминания, результат тот же до бита (доказанные места и ошибки сверены на 524 программах
  тестов с запоминанием и без):
  - **функция между кругами:** функция пишет вклад в свою сводку и запоминает, какие общие
    сводки читала (`OverflowCheck::FunctionMemo`); если ни одна прочитанная не изменилась в
    последнем слиянии, функция не анализируется, а её прошлый вклад добавляется заново
    (слияние ассоциативно, порядок вклада тот же). Круг отчёта — всегда полный.
  - **цикл внутри функции:** в «тихих» проходах (без ошибок и вкладов) результат цикла зависит
    только от состояния на входе, поэтому `LoopRanges` помнит его по точному состоянию (с
    базами и причинами) и контексту (кадр, цели `break` / `continue`), вместе с тем, что цикл
    добавил во внешние `break` / `continue` / `return`; не помнит, если в результат ушла база,
    созданная внутри, или если работа подходит к бюджету.
  На `bench/scale` (1 млн строк, мало вложенных циклов) — без изменений (~300 мс).
- **Что дальше.** Чтобы проверять по одному модулю, проверке нужна запись модуля как вход:
  объявления и выведенные сигнатуры чужих модулей — из их записей, а не из их AST; тогда правка
  в теле функции перепроверяет один модуль, а неизменная сигнатура останавливает волну. Это
  переделка `Checker` (сейчас он держит всю программу и глобальные таблицы типов) — несколько
  недель. После неё — диск (LMDB, свой двоичный формат вместо JSON: сейчас записи на 1 млн строк
  — ~60 МБ JSON и 10 с на чтение) и ускорение самой проверки (плотные массивы, имена числами).
