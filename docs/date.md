# Даты: `Date`

Решения, принятые 23 октября 2026 года. Пока ничего из этого не реализовано, кроме того, что
перечислено в [io.md](io.md) (`Date.now()`, `performance.now()`): порядок работ — в конце, в
разделе «План реализации».

## Коротко

- `Date` — как в JS: те же методы и тот же результат, что у node.
- Часовые пояса: если программа работает с местным временем или поясами, в exe встраивается
  вся база, около 150 КБ. В Windows база берётся из системы.
- Языки (`toLocaleString`, `Intl.DateTimeFormat`): встраиваются только те, что названы в коде.
  Если язык становится известен только во время работы — все. В Windows — из системы.
- Ловушки, которые видны прямо в коде, — ошибки компиляции.

## 1. Что просто

Дата в JS — число миллисекунд с 1970 года по UTC. Всё, что работает с ним напрямую, —
арифметика без данных: `Date.now()`, `new Date(ms)`, `getTime()`, `getUTC…` / `setUTC…`,
`toISOString()`, `toJSON()`, `Date.UTC(…)`, сравнение и вычитание дат.

## 2. Часовые пояса

`getHours()`, `getDate()`, `toString()`, `new Date(2026, 9, 23)` и остальное «местное» считают
по правилам пояса: кто когда переводит часы. Правила меняют правительства, база IANA
обновляется несколько раз в год.

- **Linux и macOS:** вся база (418 поясов) встраивается в exe в формате ICU — около 150 КБ
  (`zoneinfo64.res` в Windows — 148 КБ). Встраивается, только если программа работает с местным
  временем или поясами (`timeZone: "Asia/Bishkek"`); программа на `Date.now()` и UTC ничего не
  платит. В Docker `FROM scratch` своей базы нет — поэтому своя. node тоже носит базу с собой.
  Для сравнения: Go в таком контейнере без `import _ "time/tzdata"` молча считает в UTC, с ним
  exe растёт на 400 КБ.
- **Windows:** база — из ICU самой системы (Windows 10 1903+), exe не растёт.
- **Какой пояс местный** — как в node: переменная `TZ`, иначе система; ничего нет — UTC.

## 3. Языки

```ts
d.toLocaleDateString("ru-RU", { day: "numeric", month: "long", year: "numeric" })
                                          // "23 октября 2026 г."
d.toLocaleDateString(lang)                // язык из переменной
d.toLocaleString()                        // язык системы: "23.10.2026, 00:00:00"
```

Названия месяцев и дней, порядок, форматы всех языков — база CLDR. То же правило — для чисел,
сортировки строк и остального `Intl` ([intl.md](intl.md)). Все языки — 31 МБ данных
ICU (в них не только даты); в каждый exe их не положишь.

| Язык | Что попадает в exe |
|---|---|
| назван в коде строкой: `"ru-RU"` | только он — десятки КБ |
| из переменной | все языки — мегабайты |
| без аргумента — язык системы | Linux: все языки (язык системы при компиляции неизвестен) |
| любой, в Windows | ничего: ICU самой системы |

Результат — как у node. В контейнере язык системы обычно не задан, и тогда и node, и tz
пишут по-английски. В Windows ICU системы может быть другой версии, чем в node: редкие мелочи
форматирования (например, вид пробела перед временем) могут отличаться.

## 4. Разбор строк

- Формат ISO (`2026-10-23T10:00`, `2026-10-23T10:00:00.000Z`, с поясом `+06:00`) — по
  стандарту.
- Остальные форматы стандарт не описывает, и каждый движок разбирает их по-своему. tz
  разбирает так же, как V8: `"2026/10/23"`, `"Oct 23 2026 10:00"`,
  `"Fri, 23 Oct 2026 10:00:00 GMT"` (так пишет `toUTCString()`) — результат совпадает с node.
- Строка, которую разобрать нельзя, — `Invalid Date`, как в JS: `getTime()` — `NaN`,
  `toISOString()` бросает `RangeError`.

## 5. Ошибки компиляции

Только там, где всё видно в коде: строка или числа написаны прямо в нём.

| Код | node | tz |
|---|---|---|
| `new Date("23.10.2026")` | `Invalid Date` | ошибка: строка не разбирается |
| `new Date("2026-10-23")` | полночь UTC: в поясе UTC+6 `getHours()` — 6 | ошибка → `"2026-10-23T00:00"` (местное) или `"2026-10-23T00:00Z"` (UTC) |
| `new Date(2026, 1, 31)` | 3 марта | ошибка: в феврале 2026 года нет 31-го |
| `new Date(2026, 12, 1)` | 1 января 2027 | ошибка: месяцы — от 0 до 11 |
| `d.getYear()` | `126` — год минус 1900 | ошибка → `getFullYear()` |

- То же для `Date.parse("…")` и `Date.UTC(…)`.
- День `0` разрешён: `new Date(2026, 2, 0)` — последний день февраля, известный приём.

## 6. Как в JS

- `Date` изменяемый: `setDate(1)` меняет объект, и это видят все, у кого он есть. При
  параллельном async ([async.md](async.md)) — общие данные, доступ по очереди.
- Месяцы — с нуля: `new Date(2026, 9, 23)` — 23 октября. Если месяц вычислен, ошибиться
  на единицу компилятор не заметит.
- `console.log(d)` печатает как node: `2026-10-22T18:00:00.000Z`.
- `Temporal` (новое API дат в JS: неизменяемые даты, месяцы с 1, пояс явно) — когда появится в
  node и TS. В node 24 его нет.

## План реализации

На каждом шаге: тесты `tests/run` с `// same-as-node` и заданным `TZ`, ошибки в
`tests/errors`, обновление README.

1. **Простая часть** — раздел 1, печать как в node, ошибки компиляции из раздела 5.
2. **Пояса** — местные `get…` / `set…`, `toString`, `toDateString`, `toTimeString`,
   `getTimezoneOffset`, `TZ`; база в exe для Linux, ICU системы в Windows; встраивание базы
   только при работе с местным временем.
3. **Разбор строк** — ISO и разборщик, как в V8; сверка с node на наборе строк.
4. **Языки** — `toLocaleString`, `toLocaleDateString`, `toLocaleTimeString`,
   `Intl.DateTimeFormat`; данные CLDR в exe по правилам раздела 3, ICU системы в Windows.
